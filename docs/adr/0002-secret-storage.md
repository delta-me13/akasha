## 1. 背景与范围

阶段 4 要落一个**装着私钥**的库。`scope.md` §6 已经定了引擎与加密（SQLite + SQLCipher）、
以及三条约束（口令派生、口令不落盘、库里不存绝对路径），但**没有定值**：
KDF 用什么参数、盐放哪、导出文件长什么样、Bitwarden 缓存的"同级"具体指什么。本文把值定下来。

**为什么这些值得一份 ADR**：它们决定**磁盘上的位与字节**。用户存进第一把私钥之后，
改这些决定不是改配置，而是**迁移用户数据**；而迁移里最典型的失败是"能开，但内容不对或少了"。
按 [`docs/adr/README.md`](./README.md) 的门槛，这同时满足"不可逆"与"日后一定会被问为什么不用 X"。

**本文不管什么**（都是可逆项，不该混进来）：

| 项 | 去哪 |
|---|---|
| 表结构与字段集（四套池的列、索引、BW 缓存的列） | plan 0403 |
| 解锁界面、口令强度提示、自动锁定与超时 | `scope.md`；**锁定时机已定**（plan 0407）：只有显式锁，不做空闲超时 —— 见 D5 最后一条 |
| 导出的落点选择、确认框文案、导入时合并还是替换 | plan 0404（**已定**：调用方给显式路径 / 逐字短语 / **替换**而非合并） |
| 连接级开关（`cipher_memory_security` / `foreign_keys` / `busy_timeout`） | §6 |

## 3. 逐条展开

### D1 一个库文件承载全部池

**决定**：四套池（密钥 / ssh 配置 / serial 配置 / 端口转发规则）与 BW 缓存存在**同一个**库文件里，
文件名为 `akasha.db`，放在与 `config.json` **同一个数据目录**（便携目录 `akasha-data/` 与
退回 OS 目录的判定沿用 `src-tauri/src/config.rs`，本文不改那套规则）。
库文件不存在时在数据目录里创建；**数据目录本身仍不自动创建**（`portable.md` §3.1）。

**理由**：① 解锁一次 = 一次口令输入 + 一次 KDF 代价，拆成四个文件就是四次；② 导出/备份是**一个文件**，
与 P2"搬走文件夹"同向；③ 跨池一致性（主机行与它引用的密钥）能在**一个事务**里保证。

**否决的替代路**：每池一个文件 —— 四次解锁、四份导出、跨池引用只能靠约定维护，
换来的只是"某个池损坏不影响别的池"，而这种损坏在加密库里本来就等于整库不可用。

### D2 参数集：全部取 SQLCipher 4 的默认值

**决定**：不设置任何覆盖默认值的参数。冻结下来的取值：

| 项 | 取值 |
|---|---|
| 加密算法 | AES-256-CBC + **每页** HMAC-SHA512 |
| KDF | PBKDF2-HMAC-SHA512，**256,000** 次迭代（等效 512,000 次 SHA512 运算） |
| 盐 | 16 字节随机，存于库文件头部前 16 字节 |
| 页大小 | 4096 |
| `auto_vacuum` | 默认（`NONE`） |
| `cipher_compatibility` | **不使用**（它会把参数集切到旧主版本上） |

**理由**：非默认值必须**每次打开都重新声明**（`kdf_iter` / `cipher_page_size` / `cipher_hmac_algorithm`
都是如此），而"每次打开都要声明的东西"就必须有个地方存它 —— 那正是 §4 里被否掉的旁挂文件问题，
只不过换了个名字。默认值还有一个好处：它随 SQLCipher 自己演进，升级时由上游的
`cipher_migrate` 负责，我们不自建一套参数管理。

**否决的替代路**：调高 `kdf_iter` —— 见 §4 第 1 条（同一个"值存哪"的问题）。

### D3 KDF：用 SQLCipher 原生的口令派生

**决定**：口令就是 SQLCipher 传统意义上的口令（**不是**原始密钥）—— 由 SQLCipher 做
PBKDF2-HMAC-SHA512（256,000 次）派生出 256 位库密钥；盐由 SQLCipher 随机生成并保存在库文件头部，
**不需要任何旁挂文件**。

**理由**：选 SQLCipher 的目的就是把这些最容易出错的东西（盐、每页 IV、HMAC、rekey）交给一个
被广泛审计的库。选完它再绕开它的 KDF，等于只留下"文件格式是它定的"这一半好处，另一半自己重写。

**代价（照实记）**：PBKDF2 抗 GPU / ASIC 的能力不如内存硬（memory-hard）的 KDF。
详见 §4 第 1 条的量化与"为什么现在不换成 Argon2id"，以及 §5.2 **可原地升级**的路径。

### D4 口令经 C API 送入，不进 SQL 文本

**决定**：用 `sqlite3_key()`（经 `rusqlite::ffi`，即 `libsqlite3-sys`）设置密钥，
**不使用** `PRAGMA key = '…'` 的文本形式。`sqlite3_key` 由 `PRAGMA key` 内部调用
（上游文档明确），所以**磁盘上的字节完全一致** —— 这里换的是**秘密经过的路径**，不是格式。

**理由**：① 文本形式会把口令写进一条 SQL 语句里，于是它有机会出现在错误消息、
`cipher_log`、语句追踪里 —— 而日志是我们**自己写盘**的东西；② 转义：口令里有 `'`、`\`
或非 UTF-8 字节时，字符串形式要么报错要么被改写（"口令里有个引号就打不开库"这类 bug）；
③ C API 显式传长度，不必假设 NUL 结尾。

**配套约束**：`sqlite3_key` 必须**先于任何会读页的操作**。SQLCipher 是"首次用到密钥时才派生"，
所以 `journal_mode` / `foreign_keys` 之类一律排在它后面。这条约束值得写在这里而不是注释里：
违反它的表现是**库打不开**，而错误信息不会指向"你少调了一次 key"。

⚠️ plan 0402 把这条措辞改精确了：原写"必须是打开之后的**第一个**操作"，而实测表明
`PRAGMA cipher_memory_security = ON`（§6）**排在它前面既合法又更优** —— 那句 pragma 由
SQLCipher 自己拦截、不读库，而排在 `sqlite3_key` 之前才能让 codec context 里那份口令副本
落在安全分配器上。所以这条约束的实质是"**先于读页**"，不是"字面上第一个"。
调用它是 `unsafe`（`ffi`），按 `AGENTS.md` §3.4 要 `// SAFETY:` 注释 + 单测覆盖 ——
那条单测就是 plan 0401 的判据本身（错误口令打不开、正确口令打得开）。

**这不是格式级决定**（改它是改调用，不是迁移数据），写进 ADR 是因为它守着"口令不出现在 SQL 文本"，
而这条纪律日后很容易被"简化"回去。

### D5 口令不落盘、空口令被拒、遗忘即不可恢复

**决定**：

- 口令只以**字节缓冲**存在于内存：解锁/建库那一次调用用它派生密钥，之后它**在解锁窗口里**
  继续受保护地住着（见本节最后一条），窗口一结束就没有了。不进 `String`、
  不进配置文件、不进环境变量、**不作为命令行参数**（会进 `ps` 与 shell 历史）、
  **永远不进日志**（`docs/logging.md` 的字段表里没有这一项，将来也不加）。
- **空口令在应用层被拒绝**。机制（§7 实测，2026-09-12）：`sqlite3_key()` 在长度为 0 时
  **直接返回 `SQLITE_ERROR`、根本不挂 codec**，而**连接随后照常可用** —— 于是"没检查返回值"
  的后果就是得到一个**明文库**，且之后每一步都"成功"。空 key 只允许出现在**用户显式选择
  明文导出**的那条 `ATTACH … KEY ''` 路径上（那里"不加密"正是本意）。
- `Passphrase` 类型（plan 0402）：空值**造不出来**（构造即校验，且是唯一的构造口）、
  没有 `Debug`（`{:?}` 是**编译错误**，不是打码）、没有 `Display` / `Serialize`、
  `expose()` 只对本 crate 可见。于是上面三条不是纪律而是**类型事实** ——
  没有哪条调用路径需要记得检查它们。
- **口令在内存里也受保护**（plan 0406）：它不住在普通堆上，而是住在一整页
  **`mlock` 住、静止态 `PROT_NONE`、不进 core dump（`dd`）、fork 后清零（`wf`）**的内存里
  （`memsafe::Secret<[u8; N]>`），读取是一次需要 `&mut` 的**提权动作**，释放时逐字节 volatile
  擦零；调用方交进来的源缓冲也被上游擦了零。实测值见 §7.2。
  ⚠️ **边界照实写**：这挡的是"意外"泄露（越界读、误格式化、core dump、swap、fork）；
  挡不住已经能在本进程里执行代码的人 —— `/proc/<pid>/mem` 的读走 `FOLL_FORCE`，
  绕过页保护，那一页照样读得出来（§7.2 有一条**专门记录这件事**的测试）。
- **不存在找回机制**：口令丢失 = 数据不可恢复。没有恢复码、没有后门、没有"官方帮你开"。
- **解锁窗口里它一直住在那一页里**（plan 0407）：`Unlocked` 同时持有解好的连接与口令，
  两者**同生共死** —— 于是"锁定"只有一种写法（把整个 `Some` 换成 `None`）。它必须留着，
  因为导出那条"独立口令"检查（D6）要在窗口内拿得到库口令，否则用户得为一次导出重新输一遍。
  代价照实记：窗口期间多 4 KiB 的 `VmLck`（实测 §7.5）。
  什么时候结束这个窗口：**只有显式锁** —— 关窗口不锁（它的语义是**收托盘**，进程、会话、
  终端缓冲全都留着）、进程退出不锁（进程一死，解好的连接与那一页一起消失，写 exit hook
  只是仪式）、也不做空闲超时（没有 UI 也没有配置项，它要防的事与锁屏是同一件，交给 OS）。
  ⚠️ **口令经 IPC 进来的副本**：我们自己那份在 `into_bytes()` → `Passphrase::new` 时被上游擦零，
  而 tauri 内部那两份（请求体缓冲、`serde_json::Value`）**够不着** —— 边界见 §7.5。

**理由与权衡**：这些是 P1（不依赖 OS keychain）的直接后果 —— 唯一能保管的秘密就是用户的口令，
所以"恢复能力"与"不依赖操作系统组件"是一对不可兼得的东西。选 P1 就等于选了后者。
代价必须说清楚：**用户忘了口令，我们只能告诉他数据取不回来**。

### D6 导出容器：与库同格式

**决定**：

| | 做法 |
|---|---|
| 加密导出 | `ATTACH '<目标>' AS export KEY ?`（口令走**绑定参数**）+ `SELECT sqlcipher_export('export')`，再显式写版本字段 |
| 明文导出 | **同一段代码**，只是 key 参数为空（空 key **参数**与 `KEY ''` 等价，实测 §7.4：不挂 codec）；由二次确认门槛与文件名区分，不由另一条实现路径区分 |
| 还原（导入） | 用**来源口令**打开导出件（走 `open`：解锁、校验版本、查四张表），再按同一条 `sqlcipher_export` 写进**空的**库槽；那里已有内容 → 拒绝 |
| 自包含 | 盐在导出文件自己的头部 —— 导入端只需要口令，不需要任何旁挂文件 |
| 落点 | 先写临时名，成功后**原子改名**；权限 0600；用户显式选择路径（不许默认写进共享目录） |
| 内容 | 带**全部用户数据**（四套池 + BW 导入池），**不含**纯派生缓存。逐表清单在 plan 0404 收口；判据是"丢了它，用户要不要重新去上游取一次" |
| 明文导出的额外要求 | 文件名必须自曝（含 `plain`）、必须二次确认并明示"含私钥"、不许作为默认选项 |

**理由**：复用同一个格式，就复用同一个读者、同一个写者、同一套参数与同一批已测过的代码路径。
自造一个容器（magic + 头部 + 密文）意味着**恢复路径是全新的、没被日常使用检验过的代码** ——
而恢复路径的 bug 是最贵的一类：用户只有在需要它的时候才会发现它坏了。

**落地形态（plan 0404）**：上表那三条要求不是措辞，而是 API 形状 ——
① 明文导出只收 `PlaintextAck`，而它唯一的构造口要求**逐字**敲对一句后果说明
（没有 `Default`、不从 `bool` 造，于是"没有确认"在编译期就走不到那条路）；
② 文件名不含 `plain` → 直接拒绝，**目标路径上什么都不写**；
③ 导出口令与来源口令相同 → 拒绝（导出件会被写进 U 盘、发到别处、抄在便签上，
它一旦用库口令，扩散出去的是**能打开整库**的那把）。
还原定为**替换**：只写进空的库槽，不做合并 —— 合并要处理四套池的重名与
`key_id` / `jump_id` / `host_id` 的重新编号，做一半的合并就是静默丢数据。

**否决的替代路**：自定义容器（AEAD 包一层）—— 见 §4 第 4 条。

### D7 版本字段：`PRAGMA user_version`

**决定**：`user_version` 是**格式版本**的**唯一权威**，v1 = `1`。

- 打开时比较：`== 1` 继续；`> 1` **明确拒绝**（"这个库是更新版本的程序写的"），不猜测未来格式；
  `< 1` **也拒绝**（v1 之前没有版本 —— "走迁移"是留给将来的 v2 读 v1 的，
  把来路不明的 0 当"待迁移"接下去正是"能开但内容不对"的入口；plan 0402 实现时改的措辞，见 §10）。
- `meta` 表（`app_version` / `created_at` 等）只供诊断，**不参与任何打开判定** ——
  两个地方都放"版本"必然漂移，所以只允许一个地方是权威。
- ⚠️ 实测要点：`sqlcipher_export` **不传递** `user_version`（上游文档明确，`auto_vacuum` 同样不传），
  所以导出之后必须**显式写**，否则每个导出文件都是版本 0。
- **v1 的完整含义 = 版本号 + 四张表**（plan 0403 起）：`create` 在**一次事务**里建四张表并写
  `user_version = 1`，`open` 除版本号外还确认这四张表都在（缺一张 → `MissingTable`）。
  只查版本号会让"有版本号、没表"的库开起来像个空库 —— 那正是本条要防的"能开但内容不对"。
  列的**形状**仍由 `user_version` 负责：v1 一旦发布，改列就是 v2 加迁移
  （形状快照测试见 `crates/akasha-store/tests/schema_contract.rs`）。

**理由**：它是 SQLite 头里现成的 32 位整数，无需额外结构，且判据是"整数比较"而不是
"解析某个字符串"。已导出的文件会长期存在于用户的抽屉里，读者必须能认出**历史**导出。

### D8 不用 WAL

**决定**：不启用 WAL；`journal_mode` 保持默认的 `DELETE`。库里不应长期出现 `-wal` / `-shm` 文件。

**理由**：WAL 的收益是**多读者 / 单写者并发**，而我们是"单进程 + 一个专用线程"（`scope.md` §6），
没有并发可换。代价却是实打实的：WAL 模式下**单独复制 `.db` 文件会丢掉最近的已提交事务**，
而 P2 的判据正是"把文件夹搬走，数据还在"。用默认的 rollback journal 时，一个静止的 `.db`
就是一个完整一致的库。

**否决的替代路**：WAL + 提醒用户"拷贝时要连 `-wal` 一起拷" —— 把正确性押在用户记得住一件
他根本看不见的事上。

### D9 库里不存绝对路径，库内不做二级加密

**决定**：

- 任何池的字段都不得保存绝对路径。私钥以**文本列**存在库里（本来就不落临时文件，
  见 `scope.md` §3），因此不存在"密钥文件路径"这种字段。导出文件同理：导出的是逻辑数据，
  不带本机的任何位置信息。
- 库内**不再对私钥做二级加密**（整个库已经是密文）：多一层加密就多一把要管理的密钥，
  而它挡不住任何"已经拿到库和口令"的人。

**理由**：`portable.md` §2 第 2 条 —— 存了绝对路径，搬家后它们全部失效，而且失效是**静默的**。
这是数据模型层面的约束，不是目录结构层面的，所以只有写在 ADR 里才守得住。

### D10 Bitwarden 缓存的"同级"= 同一个库

**决定**：`scope.md` §7 要求的"缓存静态保护强度必须与本地池同级"，具体含义是
**存在同一个 SQLCipher 库里、用同一把口令派生的密钥、由同一次解锁打开**。

- 因此不存在第二个密钥、第二次口令输入、第二套保护强度，也不存在"缓存忘了加密"这条分支。
- 缓存里**不再做二级加密**；`fingerprint` 是**完整性自检**用的，不是加密
  （展开见 [`bitwarden.md`](../bitwarden.md) §5）。
- **不复制 `bw` 自己的 appdata 目录**：那在我们的数据目录之外（违反 P2 的落点），
  且它的保护强度由 Bitwarden 决定、不由我们承诺。我们只经 `bw` 的接口取数据，落进自己的库。
- 入库的只有**条目数据**；`BW_SESSION` 与主密码只在内存（`scope.md` §7 已定，此处只是重申边界）。

### D11 明文配置不入库

**决定**：`config.json`（目前只有 `close_behavior`）**保持明文、保持不入库**。
本 ADR 据此**否决** plan 0403 前置检查里"把配置文件并入本库"的设想。

**理由**：关窗行为必须在**解锁之前**就可用 —— 窗口可能在用户还没输入口令时就被关掉，
而那时读不到加密库里的任何东西。把明文配置搬进加密库，等于让"关窗是收托盘还是退出"
依赖于解锁状态。库只管机密与池。**因此它也不进导出文件**：它不是池数据，搬运它就是复制一个文件。

### D12 权限与不可写时的行为

**决定**：

- unix 上库文件建为 0600、导出文件同为 0600（Windows 无等价物，如实记为不做）。
  这是**尽力而为的额外一层**，不是安全边界 —— 安全边界是"文件是密文"，
  所以不因为设了权限就降低对加密的要求。
- 便携模式下数据目录**不可写**时：启动即**明确报错**，不静默退回 OS 目录
  （`portable.md` §2 第 3 条 / §4 第 3 条）。落地形态（plan 0405）：`.setup()` 在**窗口与托盘之前**
  判一次，不通过就一条 `error`（带 OS 自己的错误原文）+ **退出码 2**；判"可写"的方式是**真的写一个
  探针文件再删掉**（mode 位看不出 ACL / 只读挂载 / squashfs）。⚠️ 已知边界：这是"日志 + 非零退出码"，
  **不是弹窗** —— GUI 上的错误呈现属于真实 UI 阶段。

**理由**：静默退回的后果是"用户以为数据在 U 盘上，实际在本地磁盘；他拔了 U 盘，数据没了，
而他不知道"—— 这正是 P2 存在的理由。

### D13 内存中的机密统一经 `memsafe` 的受保护页

**决定**：进程里**长住**的机密 —— 口令、私钥、会话令牌、Bitwarden 主密码与 `BW_SESSION` ——
一律放在 `memsafe::Secret<[u8; N]>`（同一族的 `MemSafe<T>` 用于非机密的内存防护）的受保护页里：
`mlock` + 静止态 `PROT_NONE`（Windows 是只读）+ Linux 的 `MADV_DONTDUMP` / `MADV_WIPEONFORK`
+ 释放时 volatile 擦零 + 源缓冲擦零。**不自己写** `mlock` / `mprotect` / `VirtualLock` 的封装。

**理由**：这件事的难点不在密码学，而在**平台**。Unix 的 `mmap` + `mprotect` + `mlock` + `madvise`
与 Windows 的 `VirtualAlloc` + `VirtualProtect` + `VirtualLock` 是三套东西，再叠上 macOS 缺
`MADV_DONTDUMP` / `MADV_WIPEONFORK` 的分支 —— 自研意味着两百来行 `cfg` 分叉加一堆 `unsafe`，
而 `AGENTS.md` §3.4 那条"`unsafe` 只许出现在 `akasha-store`"正是靠**不自己写这种东西**守住的。
本仓库今天有 Linux 与 Windows 在矩阵里、macOS 在类型检查里，四平台是目标（§12）。

**实测过它真的跨平台**（plan 0406）：`memsafe` 为 `x86_64-pc-windows-msvc` 与
`aarch64-apple-darwin` 都**编得过**（`cargo check --target …`，不是读 `cfg` 猜的）；
Linux 上的四条防护见 §7.2。⚠️ "编得过"不等于"在那些平台上也做了同样的事" ——
下表就是差在哪。

**"防护足够"的判据**（不是"它号称安全"）：四条**会红**的测试 ——
① 进程级 `VmLck` 涨；② 那一页静止态没有任何权限位；③ `VmFlags` 含 `dd`；④ 含 `wf`。
**每新增一个用途都要按这张表再验一遍**：`N` 不同、生命期不同，"那一页是我们的"这个识别方式
与验证点都会变。**plan 0407 是第三次重验**（新用途：口令的生命期从"解锁路径上一小段"变成
"整个解锁窗口"）：四条判据仍成立，另外多了一条这一层独有的 —— **锁定时那一页要 `munmap`
回去**（`VmLck` 回落到起点、`---p` 段数回落）。实测值见 §7.5。

**已知不足（照实记，别把安全说大）**：

| 不足 | 后果 |
|---|---|
| Windows 静止态是 `PAGE_READONLY`（可读） | 同进程内的越界读在 Windows 上仍读得到 |
| macOS 没有 `MADV_DONTDUMP` / `MADV_WIPEONFORK` | "不进 core dump"与"fork 后清零"只在 Linux 成立 |
| `/proc/<pid>/mem` 的读走 `FOLL_FORCE` | 能在**本进程里执行代码**的人照样读得到（§7.2 有实测，且有一条测试钉住它） |
| 上游是年轻的小库（2025-02 首发、759 行、三个 owner） | 它的 bug 就是我们的 bug；复核条件见 §8 |
| `mlock` 失败 → **构造失败**（上游无降级路径） | 结果是"解锁明确失败"而不是"静默不锁"；这条怎么呈现给用户由 plan 0407 定：**一句用户能懂的话 + 下一步**（查 `ulimit -l` / 容器里的 `RLIMIT_MEMLOCK`），而不是把上游那层 `Memory error:` 包装丢给他 |
| 只能放固定大小的 `[u8; N]` | 变长机密（比如几 KB 的 PEM）要选一个够大的 `N`；**上限必须显式定义**，超了报错而不是截断 |

**不适用**：可以公开的数据；以及**已经整体加密**的东西（库文件、导出文件）——
它们的安全边界是"文件是密文"，在内存里再套一层不改变任何结论。

**否决的路**：

| 方案 | 为什么不选 |
|---|---|
| **自己写 `mlock` / `mprotect` 封装** | 见上"理由"：三套 syscall + `cfg` 分叉 + 新增一处 `unsafe`，换来的只是"少一个依赖"。真要换回自研，触发条件是 §8 那次复核 |
| **只靠 `zeroize`**（擦一个缓冲） | 挡不住 core dump、swap、fork —— 这三条恰好是真实发生过的泄露路径（plan 0402 当时的判断，已被 0406 推翻） |
| **靠 `cipher_memory_security` 一把梭** | 它只管 SQLCipher 自己分配的内存（§6）；口令在我们的进程里，不归它管。两者是**互补**的两层，不是二选一 |

### D14 不变量写进库（`STRICT` + `CHECK` + 外键），不与应用层重复

**决定**：四套池的取值域与关系（端口范围、`dynamic` 没有目标主机、`key_id` 只对
`publickey` 有意义、跳板自环、重名、删除被引用行）**写在 DDL 的 `CHECK` 与外键上**；
应用层不再各写一份校验，只负责把 sqlite 的失败翻成能读的说法（`StoreError::Conflict`）。
`PRAGMA foreign_keys = ON` 由 `open` / `create` **每个连接**开一次（sqlite 的默认是**关**）。

**理由**：三个具体后果，都不是审美问题 ——

1. **绕不过**：库自己拦下来的东西，任何一条代码路径都拦得住。写入路径会变多
   （导入、dump 恢复、将来的迁移、手工修库），而"校验写在应用层"意味着每加一条路径就多问
   一次"你记得校验了吗"；
2. **不漂移**：两处校验必然分叉，而分叉的方向通常是"库更松"（改表的人不知道应用层还有一份）。
   反过来，形状快照测试让"改列"直接红，逼出版本号；
3. **外键默认关是个陷阱**：`REFERENCES` 声明得再漂亮，不开 pragma 就**一声不响**地不生效 ——
   它有独立的读回断言（`tests/schema_contract.rs`），因为"我们以为开了"不是证据。

**代价（照实记）**：① 用 `STRICT` 表要求 SQLite ≥ 3.37（有版本断言钉着）；② 错误信息来自
sqlite，翻译成 `Conflict { pool, detail }` 会丢掉"到底是哪条约束"的结构化信息 ——
用户要做的事反正是同一件（改这一行，或先去掉引用它的东西），所以合成了一个变体；
③ 改一条 `CHECK` 也是改格式，与改列同罪。

| 方案 | 为什么不选 |
|---|---|
| **Argon2id（`argon2` crate）+ 原始密钥模式**（`PRAGMA key = "x'…'"`） | 盐必须先于"打开库"存在，而 SQLCipher 把盐存在**库文件头部** —— 于是盐只能外置：要么旁挂一个参数文件，要么用 `cipher_plaintext_header_size` + `cipher_salt` 走官方支持的外置盐路径（多一个"丢了就打不开库"的文件）。它换来的是一到两个数量级的抗暴力优势：**对强口令两者都不可行，对弱口令两者都可破**，所以它不改变结论，却把格式永久变成两文件。**而且它不必现在选** —— §5.2 给出了原地升级路径，所以今天用默认 KDF 不会锁死 KDF 的选择。若"库文件会被单独同步上云"成为真实场景，按 §8 重新评估。 |
| ↳ 它的一个更巧的变体：先用随机密钥建库 → 读回 SQLCipher 生成的盐 → 再用这个盐做 Argon2 的盐并 `rekey` | 它避开了旁挂文件，但把建库路径变成"先造一个谁都打不开的库"。中途被打断就得到一个不可用文件，而这是**凭据库**的创建路径。复杂度换来的收益与上一条相同，不值得。 |
| **口令 + 随机密钥文件**（1Password Secret Key / KeePassXC key file 式） | 那条额外的 256 位秘密只挡"库文件单独泄露、文件夹没泄露"的场景。在我们的便携模型里两者始终在同一个文件夹里，所以对常见威胁等同没有；而对用户，它制造了一类最糟的失败："我有你的库，但还缺一个文件" —— 与"程序坏了"无法区分。作为**复审项**保留（§8）。 |
| **自定义 AEAD 容器**（age / XChaCha20-Poly1305 包一层导出） | 需要新引入一条密码学路径 + 一套容器格式（magic / 版本 / KDF 参数 / 盐 / nonce 都要自己定义与向后兼容），而它解决的问题（"导出的文件长什么样"）已经被"导出 = 同格式的另一个加密库"解决。恢复路径必须是**每天都在被使用**的代码。 |
| **`bundled-sqlcipher`（不带 `-vendored-openssl`）** | 已在 `scope.md` §6 否决：四平台构建会撞系统 OpenSSL 的交叉编译问题。此处仅登记，避免重新论证。 |
| **OS 凭据库**（GNOME Keyring / Keychain / Credential Manager） | 已被 P1 否决（`scope.md` §1）。登记在此是因为它是最常被重新提出的一条。 |

## 5. 不可逆点与迁移代价

### 5.1 一旦有用户数据就改不动的

| 项 | 现在定成什么 | 改它的代价 |
|---|---|---|
| 库文件格式 | SQLCipher 4 默认参数集（D2 / D3） | 必须"读旧 → 写新"整库搬迁；`PRAGMA rekey` 能改密钥，改不了页大小之类的参数 |
| 打开顺序 | `sqlite3_key` 必须先于任何语句（D4） | 改动集中在打开函数；风险形态是"某天有人在 key 之前加了个 `PRAGMA`"，表现为库打不开 |
| 版本字段语义 | `user_version` = 格式版本，整数值（D7） | 语义一旦发布就不能改含义，只能加新字段 —— 所以它必须是整数比较 |
| 导出容器 | 与库同格式（D6） | 已导出的文件永远按当时的格式解读：读者要能读**历史**导出 |
| 不存绝对路径 | 数据模型约定（D9） | 一旦存了，搬家后静默失效，只能在整池上做一次"路径 → 标识"的清洗 |
| 空口令被拒 | 应用层校验（D5） | 若哪天放行空口令，库里就会出现"看似加密、其实明文"的文件，且对已存在的库无法追溯 |

### 5.2 将来若要换到内存硬 KDF（不是现在要做的）

顺序固定，且**旧格式在同一个实现里继续可读**：

1. 按旧路径打开库，读 `PRAGMA cipher_salt` 拿到当前 16 字节盐；
2. 把新方案写进旁挂参数文件（`kdf` / 参数 / 盐）—— 从这一刻起它成为打开所必需的文件；
3. `sqlite3_rekey` 把库密钥换成"由口令 + 盐经 Argon2id 派生"的原始密钥；
4. 之后打开：有参数文件走新路径，没有则走旧路径。
   实现时须实测**rekey 是否保持盐不变**（决定第 1 步与第 3 步的先后）；若变，改用
   "导出 → 用新参数写回"的搬家路径（慢但确定）。

**因此**：今天选默认 KDF **不会**锁死 KDF 的选择 —— 这正是 §4 第 1 条敢把它推迟的理由。

## 7. 实测结果（plan 0401 跑完，2026-09-12）

契约测试落在 `src-tauri/crates/akasha-store/tests/sqlcipher_contract.rs` —— 上游换版本时它们该红，
而不是让本文里的一段推断悄悄失效。

| 要实测的 | 实测结果 |
|---|---|
| `PRAGMA cipher_settings` 的实际输出 | 一列 `pragma`，每行 `PRAGMA <名> = <值>;`；取值与 D2 **完全一致**（`kdf_iter = 256000`、`cipher_page_size = 4096`、`HMAC_SHA512`、`PBKDF2_HMAC_SHA512`），且 `journal_mode` 就是 `delete`（D8） |
| `sqlite3_key` 经 `rusqlite::ffi` 可用 + 版本 | 可用（`rusqlite 0.32.1` → `libsqlite3-sys 0.30.1` → **SQLCipher 4.5.7 community**，与预期一致）；provider `openssl`、**OpenSSL 3.6.3**（`openssl-src 300.6.1+3.6.3`，vendored） |
| 错误口令的报错形态 | `SqliteFailure(Error { code: NotADatabase, extended_code: 26 }, Some("file is not a database"))` —— 与预期一致 |
| 空口令走 `sqlite3_key` 的后果 | ⚠️ **与预期不同**：`sqlite3_key_v2` 在 `nKey == 0` 时直接 `return SQLITE_ERROR`、**根本不挂 codec**；而**连接随后照常可用** → 得到一个明文库。见 D5 与 §10 |
| 明文导出的 round-trip + `user_version` | 通过；`user_version` **确实不传递**（源库 7 → 导出 0），源库自身不受影响（D7 的前提成立：导出时必须显式写版本） |
| `.db` 里 grep 不到明文私钥 | 8192 字节的库里 **0** 命中；头部不是 `SQLite format 3`；对照组的空 key 库 **1** 命中（说明这条 grep 真的能搜到东西） |
| `rekey` 之后盐是否变化 | **不变**（前 16 字节逐字节相同）→ §5.2 的第 1 / 第 3 步顺序不变，不需要退到"导出再写回"的搬家路径 |

**额外实测（不在原清单里，但影响实现）**：

- **库文件权限**：SQLite 自己建出来是 **644**，不是 0600 —— D12 那条不是装饰，得显式设。
- **rusqlite 的版本不是我们选的**：`victauri-plugin` 已依赖 `rusqlite ^0.32`，而 `libsqlite3-sys`
  带 `links = "sqlite3"`，cargo 不允许同一原生库出现两个版本（实测直接被拒）。
  好在 features 取并集，全 app 只有一个 sqlite，且是我们指定的 SQLCipher 那一支。

### 7.1 plan 0402 的实测（2026-09-12）

契约测试落在 `src-tauri/crates/akasha-store/tests/`。**最要紧的一条是推翻了一个隐含假设**：

| 要测的 | 实测结果 |
|---|---|
| 文件不存在 / 0 字节时用**任意**口令 `open` | ⚠️ **能打开**：库是 0 字节、没有任何东西可解，KDF 根本没跑（**~0.19 ms**，对比真实解锁 **~105 ms**）。→ "错误口令打不开"只在**已经有内容**的库上成立，所以打开与新建必须是两条路（见 §2 的 D7 行与 plan 0402） |
| 写出 `user_version = 1` 之后 | 文件 **4096 字节**、头部非 SQLite 魔数、正确口令读回 `1`、错一个字节 → `NotADatabase`。**口令从这一刻起才有约束力** |
| `PRAGMA cipher_salt` | 32 位十六进制，**逐字节等于文件头前 16 字节**（D2 的"盐存于头部前 16 字节"由此证实）；同一口令建的两个库盐不同、字节不同 |
| 解锁耗时 | **105–108 ms**（256,000 次 PBKDF2-HMAC-SHA512，本机）；**错误口令也是 ~104 ms** —— KDF 先跑完，读页才失败。§8 的"低端机"复审条件拿这个数当基线 |
| `cipher_memory_security` | 默认 **0**；设 `ON` 后读回 `1`；**设 `OFF` 关不掉**（上游 `sqlcipher_set_mem_security` 的实现是 `if(on) { … }`）；读回值是 `on && executed` 的合取；**进程级**全局，不是连接级 |
| 明文 sqlite 文件喂给打开路径 | `NotADatabase`（读第一页就失败）→ 版本校验不可能被一个明文库骗过 |
| `sqlite3_key` 排在 `cipher_memory_security` **之后** | 可以，库照样是加密的 —— 这就是 D4 的措辞能改精确的依据 |

**另有一条与本文无关但影响本仓库门禁的实测**：cargo-deny 默认只把 manifest 指向的那个包当图根，
而本仓库的 workspace root 同时是一个真实包（`akasha`），于是 `crates/*` 里**尚未被 app 依赖的成员
连同它们独有的整棵子树都不在图里** —— `[bans] deny` 写了 `keyring` 也静默不生效
（plan 0402 才发现；`--workspace` 已加进 `just deny` / `just deny-offline`）。

### 7.2 口令的内存防护（plan 0406 实测，2026-09-12）

| 要测的 | 实测结果 |
|---|---|
| 静止态的权限 | smaps 里那一页是 **`---p`**（匿名、无任何权限），正好 **4096 字节**；判据是"建口令前后各取一次快照，多出来的那一页" |
| `mlock` | 进程级 `VmLck` **0 kB → 4 kB** |
| `VmFlags` | `mr mw me lo ac wf dd sd` —— **`dd`（`MADV_DONTDUMP`）与 `wf`（`MADV_WIPEONFORK`）都在**（上游只对 Linux 设这两条） |
| `/proc/self/mem` | ⚠️ **读得出来**（`Ok(4096)`，内容就是口令）：`FOLL_FORCE` 绕过页保护。所以这一层挡的是"意外"，不是"对手" |

⚠️ **本环境的一个坑**（写测试时踩到）：`/proc/self/smaps` 在这里**没有 `VmLck` 字段**
（`VmFlags` 有），验 `mlock` 要用 `/proc/self/status` 的进程级 `VmLck`；
而 smaps 的属性行**带缩进**，`strip_prefix` 之前必须 `trim_start()`。

**一条没能验证的**：源缓冲的 volatile 擦零（上游 `Cell::from_bytes` 的契约）——源已经被移走，
测不到，只能读源码（`cell.rs:264` 的 `secure_zero`）并把它记成"靠上游"的一条。

### 7.3 四套池落地时的实测（plan 0403，2026-09-12）

| 要测的 | 实测结果 |
|---|---|
| 建库后的库文件大小 | **36864 字节 = 9 页**（v1 的四张表 + `sqlite_master` 等）。⚠️ 它**不是定值**：0402 时只有一页 4096，0403 建表后是 9 页。判据因此写成"非空且是整页的整数倍"，而不是钉死数字 |
| 内嵌 SQLite 版本 | `sqlite_version()` 报 **3.46** —— `STRICT` 表（≥ 3.37）可用，这条也有断言（它不认 STRICT 的表现是建表直接报错，不是静默降级） |
| 外键真的生效 | `PRAGMA foreign_keys` 读回 **1**；删除仍被 host 引用的密钥 → `Conflict`（`ON DELETE RESTRICT`），行还在 |
| 私钥那一页（D13 的判据表重验） | smaps 里多出**一页** `---p`，大小正好 **16384 字节**（4 页）；进程级 `VmLck` **68 kB → 84 kB**（+16）；`VmFlags = mr mw me lo ac wf dd sd`（`dd` / `wf` 都在）；**`drop` 之后那一页消失**（`munmap` 还回 OS） |
| 超长私钥 | 16384 字节是硬上限，超了在**构造**层就被拒（`SecretTooLong`）—— 库里因此不可能有一条"读不出来"的行 |
| 写链的深度守卫 | 跳板链在 `update` 时逐跳走一遍：成环 → `JumpChain`；库里另有一层 `CHECK (jump_id <> id)` 挡自环（绕过 API 的原始 SQL 也拦得住） |

⚠️ 同一批测试也钉住了**边界**：`/proc/self/mem` 依旧读得出受保护页（§7.2 的结论对私钥同样成立）；
Windows 的静止态是 `PAGE_READONLY`、macOS 没有 `dd`/`wf` —— 那两条判据**只在 Linux 上成立**，
所以私钥那份测试是 `cfg(target_os = "linux")` 的（D13 的不足表已经写明这不是"覆盖不到"）。

### 7.4 导出容器的落地实测（plan 0404，2026-09-12）

契约测试落在 `src-tauri/crates/akasha-store/tests/export_contract.rs`。前四条是**动手之前**先量的
（探针 `tests/scratch_attach.rs` 写完即删），因为 D6 的"同一段代码"与 D12 的 0600 都押在它们身上：

| 要测的 | 实测结果 |
|---|---|
| `ATTACH DATABASE ?1 AS export KEY ?2` 吃不吃绑定参数 | **吃**（TEXT 与 BLOB 都吃）→ 口令不必进 SQL 文本，D4 那条理由对导出同样成立 |
| 空 key **参数**（`&[]` / `""`） | **等价于 `KEY ''`**：ATTACH 成功、`sqlcipher_export` 成功，写出的是**明文** sqlite（裸 sqlite 读得到数据）→ 明文那条路确实可以复用同一段代码，不需要第二条实现 |
| 预建 0 字节 0600 文件当 ATTACH 目标 | **可以**，写完仍是 0600 → 导出件**从头**就收紧，不必"先按 umask 建出来、事后 chmod" |
| `PRAGMA export.user_version = 1`（附挂库） | **可以**，且必须显式写（§7 那条"`sqlcipher_export` 不传递 `user_version`"） |

| 产物 | 大小 | 权限 | 头部 | grep 明文私钥标记 |
|---|---|---|---|---|

### 7.5 解锁 / 锁定的生命周期实测（plan 0407，2026-09-12）

契约测试落在 `src-tauri/crates/akasha-store/tests/unlock_lifecycle.rs`：它把**整个进程内存**
（匿名段，含静止不可读的 `---p`）扫一遍找那两串字节。真路径那一半在
`src-tauri/tests/vault_unlock.rs`（真 app 上解锁 → 读一次四套池 → 锁定，
并且**从外面**读那个进程的 `/proc/<pid>/status`）。

| 时刻 | 口令出现在几处 | 派生密钥出现在几处 | `VmLck` |
|---|---|---|---|
| 解锁前 | 1（测试自己那根针） | — | **0 kB** |
| 解锁中（连接 + 口令页都活着） | **2**（针 / 受保护页） | **3**（针 / SQLCipher 两处） | **152 kB** |
| 丢掉连接 | 2（针 / 受保护页） | 1（针） | **4 kB** |
| 丢掉口令 | 1（针） | 1（针） | **0 kB**（`---p` 段数也回到起点） |

（真 app 上同一段轨迹读出来是 **0 → 192 → 0 kB** —— 数值随进程里还有什么而变，
判据是**形态**：解锁中涨、锁定后回到起点。）

三点结论，都不是推断：

1. **`cipher_memory_security` 的"释放时擦零"是真的**：派生密钥在连接 drop 之后**一处不剩**。
   它把 SQLite 的分配器换成 `sqlcipher_mem_malloc / mem_free` —— **每次分配 `mlock`、
   每次释放先擦零再 `munlock`**（vendored `sqlite3.c` 里那两段可逐行核对）。所以那 152 kB 里
   大头是 SQLCipher 自己锁的，不是我们那一页（4 kB）；而"sqlcipher 里的副本"不是靠文档相信的。
2. **SQLCipher 不留口令本体**：解锁期间口令**只**多出一处 —— 那一页 `---p`。
   所以"口令的副本清单"里**没有**"SQLCipher 内部那一份"这一行（原先是想当然地写上的）。
3. **两条扫描测试都带正对照**：解锁期间必须比基线**多**扫到 —— 少了它，"锁上之后 0 命中"
   与"扫描器根本没在工作"是同一条绿（坑 #87 的第二次适用）。

**边界（照实说，别把它说大）**：口令经 IPC 进来时，tauri 内部还有两份副本**够不着** ——
请求体的字节缓冲与 `serde_json::Value`；生命期是这一次调用，之后被 free 而**不擦**。
这一层没有接口拿到它们的 `&mut`。命令参数做成 newtype（`PassphraseInput`：没有 `Debug`、
唯一的出路是 `into_bytes()`）能保证的是**我们这一份**在搬进 `Passphrase::new` 时被擦零。
更紧的做法是让口令走 raw body（那两份里少一份、且没有文本形态），代价是前端必须手写一行
裸 `invoke`（`AGENTS.md` §0 绝对禁止 #1）—— **记为后续**，不在本步为了它破一条架构规则。

## 8. 复审条件
- **上游 SQLCipher 主版本变化 / `libsqlite3-sys` 大版本升级**：默认参数集会变，必须按
  `cipher_migrate` 评估并重跑 §7 的实测 —— 这是"取默认值"换来的成本，要认。
- **"库文件会被单独同步或备份到云"成为真实场景**：重新评估随机密钥文件（§4 第 3 条）
  与内存硬 KDF（§4 第 1 条）—— 那时"旁挂一个文件"的收益第一次变得真实。
- **低端机上解锁耗时不可接受**：届时是"降参数"（安全性下降）与"加旁挂文件"（复杂度上升）之间的选择，
  不能默默降。
- **阶段 9（Bitwarden）落地时**，若 `bw` 的实际接口形状与本 ADR 对缓存的假设不符
  （例如拿不到可校验的指纹或修订时间），回到 D10 重新定"缓存里到底存什么"。
- **`memsafe` 这条依赖变动时**（D5 的内存防护是本文唯一一处"安全属性押在第三方实现上"）：
  上游停更 / 出 RUSTSEC 公告 / 大版本改变保护语义（例如不再 `mlock`、或不再给
  `MADV_DONTDUMP`）/ 我们的平台矩阵里多一个它不支持的平台 —— 任一发生就按 §7.2 重跑一遍，
  并重新评估"自己写那几十行 syscall"与"换一个被审计过的库"。
  `tests/passphrase_contract.rs` 里那两条测试**就是为此存在的**：上游一改，它们会红。
