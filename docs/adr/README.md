# 架构决策记录（ADR）

终端项目的选型易错点多，且容易被反复推翻。任何**不可轻易撤销**的决定都要在这里留痕
（见 `AGENTS.md` §8）。

约定：文件名 `NNNN-<slug>.md`，编号连续不重用。

### 状态：三态 —— "可以开始实现"与"不可再改"是两件事

| 状态 | 含义 | 本文能改吗 |
|---|---|---|
| **提议中**（Proposed） | 草案。还没人在它上面写代码 | 随意改 |
| **实现中**（Implementing） | 已同意按它动代码 | **可以改** —— 实现会暴露架构问题，坚持不改才是错误的做法。每次改动在文末「修订记录」记一行：日期 + 改了什么 + 为什么 |
| **已定案**（Frozen） | 落地它的 plan 全部完成 | **不可改**，只能被新 ADR 取代 |

推进的判据：**提议中 → 实现中** = 决策者同意动代码；**实现中 → 已定案** = 落地它的
plan 全部完成（在那些 plan 归档时一起改）。

> ⚠️ **2026-09-12 词汇迁移**：原先把"可以开始实现"与"不可再修改"压成同一个状态
> `已接受`，结果是实现期一发现架构问题就没有合规出路 —— 要么带病实现，要么违规改 ADR。
> 现在拆成三态；0001 / 0004 / 0005 的状态词由 `已接受` 改为 `已定案`
> （**只换状态词，内容一字未动**）。

---

## 写 ADR 的门槛：两条**都**满足才写

**ADR 要少。** 一条 ADR 必须同时满足：

1. **不可逆** —— 改了要迁移用户数据、改线协议、或重写一层；不是改个配置就行
2. **会被反复推翻** —— 后人（或未来的自己）一定会问"为什么不用 X"

只满足一条的，写进 [`../scope.md`](../scope.md) 的"已定案"就够。
**决定本身不会丢**（scope.md 是能力的唯一来源），所以不必为了"记得住"而写 ADR。

> - 反面例子：把"点叉默认收托盘"写成 ADR —— 它是可逆的配置项，scope.md 足够。
> - 正面例子：SQLCipher + 口令派生 —— 它决定**数据文件格式**，改它要迁移用户数据。

### 原来的 7~8 份合并进了这 3 份

| 私钥落盘位置 / SQLCipher / 导出 | **0002** | 全都是数据文件格式 |
| 平台矩阵与 Android 形态 | **0001** | 就是"crate 与平台边界"的一部分 |

| 0003 | **已定案**（2026-09-15）—— 落地在 [plan 0501](../plans/archive/0501-adr-0003-ssh-stack.md) 及其后的 0502–0506 与阶段 6 的 0601–0606，那些 plan **已全部完成并归档**；阶段 5 的编号于 2026-09-13 按依赖重排 |
| 0004 | **已完成**（布局修正，随时可写 —— 它记的是已发生的事实） |
| 0005 | **已完成**（plan 0205 开工时写的：那条路径已经在代码里被验证过一遍，不需要再等） |
| 0006 | **实现中**（2026-09-15，plan 0701 开工时写的）—— 落地点是 0701–0704；那些 plan 全部归档时转为「已定案」 |

> 写太早的代价是：它们会塞满**还没被代码验证过的细节**，而细节一旦被实践证明是错的，
> 改的代价随实现进度上升 —— 三态里「实现中可改」缓解了这一条，但有代价（每改一次都要
> 重读一遍当时否掉的替代路）。还没到开工时机的决定，落点是 `scope.md` 的对应章节 —— 它们不会丢。
