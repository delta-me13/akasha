# Plan 0404: dump 与导出

- **关联**：ROADMAP 阶段 4 ·「dump 与导出（可选加密；明文导出必须二次确认）」；
  ADR-0002 **D6**（容器）/ **D7**（版本字段）/ **D12**（权限）
- **前置**：plan 0403（四套池的 CRUD —— 没有数据就无从"导出后比对"）
- **状态**：已完成（2026-09-12）

## 目标

- **dump**：把"库里到底有什么"说出来，给人看、也给诊断用 —— **一个机密字节都不含**
- **导出**：可选是否加密；加密导出用**独立口令**、自包含、可直接给另一台机器用（D6）
- **导入还原**：把导出文件还原成一个能开、内容一致的库
- **明文导出**：**门槛写进实现** —— 没有确认就走不到那条路（`scope.md` §6 / D6）

## 非目标

- **本步不接进 app**：导出要读写库，而"谁持有解好的连接、口令从哪来"是 plan 0407。
  本步交付 `akasha-store` 的库函数 + 会红的测试；IPC 与确认界面跟着 0407 那一层走。
- **不合并导入**（见下表）
- 跨版本迁移（格式真变时另立）、Bitwarden 写回（`later`）

## 决定：关掉 ADR-0002 留的三个开放问题

| ADR 的待定项 | 定为 | 为什么 |
|---|---|---|
| 导入时合并还是替换 | **替换**：`restore` 只写进**空**的库槽（有内容 → `VaultExists`） | 合并要处理四套池的重名、`key_id` / `jump_id` / `host_id` 的重新编号、"哪边赢"—— 做一半的合并就是**静默丢数据**。"导出件本身就是同格式的库"（D6）让"还原"不需要新机制 |
| 导出的落点选择 | 调用方给**显式路径**，库层不做默认落点 | 默认落进共享目录 = 把含私钥的文件放到最不该放的地方 |
| 确认框文案 | **逐字敲一句短语**（`PLAINTEXT_CONFIRMATION`），不是勾选框 | 勾选可以默认勾上、也可以闭眼点；门槛要能被测 —— "不确认就走不到那条路" |

另外两条**由库强制执行**（不是纪律）：

- **明文导出的文件名必须含 `plain`**（D6 的"自曝"）：文件名不自曝 → 拒绝，不写文件。
- **导出用的口令不能是它导出时那把口令**（D6 的"独立口令"）：两把相同 → 拒绝。
  这条要在**解锁窗口内**取到库口令（0407 定"谁持有口令"时不得把它变成不可取）。

## 判据（每条都是一条会红的测试）

1. **加密导出可在另一目录还原**：源库四套池都写满 → 导出到 B 目录 → 还原到 C 目录 →
   **用 C 的口令打开并逐字段比对**（不是"能开"）；用别的口令打不开
2. **导出件本身就是库**（D6 自包含）：不还原也能用导出口令 `open`，内容与源一致
3. **加密导出里没有明文私钥**：整个文件 grep PEM **0 命中**；对照组 = 明文导出 **1 命中**
   （证明扫描器不是坏在原地）
4. **明文门槛**：短语不对 → `PlaintextRefused` **且目标文件不存在**；文件名不含 `plain`
   → 同样拒绝且不写文件；对照 = 短语对 + 名字对 → 文件在，且**裸 sqlite 读得到私钥**
   （这正是门槛要拦的那个东西）
5. **导出口令必须独立**：两把口令相同 → 拒绝且不写文件（导出与还原两条路都测）
6. **失败不留半成品**：把目标路径指到一个已存在的目录（改名那一步必失败）→
   目标不变、`…partial` 不在；父目录不存在的失败同理
7. **dump 不泄密**：`to_text()` 里 grep PEM **0 命中**，且四套池的行数与内容对得上；
   空库也 dump 得出来
8. **还原不覆盖**：库槽里已有库 → `VaultExists`，原文件的字节**一个都没变**
9. **导出不动源库**：导出 / 还原之后，源库仍能用原口令打开且 dump 一致

## 实施记录（2026-09-12）

**先量再写**（四条探针，全在动手前跑出来，探针文件写完即删）：

| 量什么 | 结果 |
|---|---|
| `ATTACH DATABASE ?1 AS export KEY ?2` 吃不吃绑定参数 | **吃**（TEXT 与 BLOB 都吃）→ 口令不必进 SQL 文本，与 D4 拒绝 `PRAGMA key = '…'` 同一条理由 |
| 空 key **参数**（`&[]` / `""`） | **等价于 `KEY ''`**：不挂 codec，写出来的是明文 sqlite（裸 sqlite 读得到数据）→ D6 的"同一段代码"成立，**不需要**第二条实现 |
| 预建的 0 字节 0600 文件当 ATTACH 目标 | **可以**，写完仍是 0600 → 导出件从头就收紧（D12），不必"先 0644 后 chmod" |
| `PRAGMA export.user_version = 1`（附挂库的 pragma） | **可以**，且必须显式写（D7） |

**实测值**（`target/store-pools/` 下的真文件）：

| 文件 | 大小 | 权限 | 头部 | grep 明文私钥标记 |
|---|---|---|---|---|
| 加密导出件 | 36864 B（9 页） | **600** | `fb2f f927 …`（随机，非 `SQLite format 3`） | **0** |
| 同数据的明文导出件（对照） | 36864 B | 600 | `SQLite format 3\0` | **1** |
| 还原出来的库 | 36864 B | 600 | 随机 | 0 |

`find target/store-pools -name '*.partial'` → **0**（失败那条路真的清干净了）。

**负例验过的地方**（不做这一步就分不清"规则在工作"与"规则什么都没匹配到"）：

- 明文门槛的"逐字"用 **7 个近似输入**试探（空串 / 前缀 / 首尾空格 / 多一个句号 / 少一个字 /
  全大写英文），全部被拒；对照组是逐字敲对 → 放行。
- `contains()` 这个扫描器有**对照组**：同数据的明文件里 grep **命中**，否则"加密件 0 命中"
  可能只是扫描器坏了。
- **清理那条路径**：把 `discard()` 临时改成空操作 → `a_failed_export_leaves_nothing_behind`
  **变红**（证明它测的确实是"改名失败之后"的清理，而不是更早的某一步失败）。

**实施中改的两处判断**：

- 多做了一个 `restore_plaintext`：只导出明文而**没有回程**的话，明文件就只能是"给别的工具
  读的死路"；回程复用同一个读者（裸 sqlite + 版本 + 四张表）与同一个写者，不新增恢复路径。
  它**没有**确认门槛 —— 门槛拦的是"留下明文"，这一步是消灭明文。
- `SharedPassphrase` 用**运行时比较**（D6 的"独立口令"）。代价是调用方必须在解锁窗口内
  拿得到库口令 —— 这条作为**约束**交给 plan 0407（它定"谁持有口令"）。

**没有做的事**（照实记）：

- **不接 app**：IPC 命令、文件选择器、确认界面都等 plan 0407（要先把"谁持有连接与口令"
  定下来）。本步交付的是库函数 + 11 条契约测试。
- **不做合并导入**（决定与理由见上表）。
- **不做跨版本迁移**：导出件与库同格式（D6），格式变了要一起迁移，那是另一件事。
- **权限位只在 unix 上有判据**（D12 的边界：Windows 无等价物，如实不做）。
- 明文导出**不做**"导出后再确认文件已落盘"的额外 fsync —— 原子改名保证的是"不存在半成品"，
  不是"断电后仍在"。要不要 fsync 是另一条要求（还没人提）。
