# Plan 0704: 并发 in-flight 请求（pipelining）

- **关联**：ROADMAP 阶段 7 ·「并发 in-flight 请求（pipelining）」
- **前置**：plan 0702（传输引擎）· plan 0703（两档共用同一个引擎）· ADR-0006 D6（上限归引擎）
- **状态**：已完成（2026-09-15）

## 目标

同一批小文件的**往返开销**由并发盖住：一次最多几个文件同时在搬（有上限、有默认值），
而落盘不变量（`scope.md` §4.2：临时名 + 原子重命名，失败 / 取消 / 关会话都删临时文件）
在并发下**逐条仍然成立**。

三件事在这里定下来：

1. **上限在哪、谁决定** —— 引擎多一个并发上限（`InFlight`）：上限是它的参数（默认值在
   `akasha-core::Config`，同 ADR-0003 D13 的口径），"此刻有几个文件在搬"是它唯一的语义。
   app 侧**一个 SFTP 会话持一个**，于是上限约束的是这个会话的**全部**传输，不区分它们来自
   几条命令。
2. **并发从哪来** —— 一个文件一条命令、一个独立任务（plan 0702 起就是这个形状），
   所以并发不需要新的编排层：12 条命令就是 12 个任务，上限只让第 9 个等一等。
   没有"整批"这个概念，也就没有"一个文件失败是否中止整批"这个问题：**每条传输有自己的结局**，
   一条失败不影响别的（第 5 步断言）。
3. **排队中被取消** —— 空位是**可取消地**等的。关会话与用户取消推的是同一个信号（D4），
   排队中的那条因此在**碰目标之前**退出；否则它会先建一个临时文件再删掉，而关会话要等它把
   这两步走完。

## 非目标

- 多路复用 / 多连接：一个 `Session` 两侧各一条连接，仍然是（ADR-0006 D3）
- 断点续传、限速、队列优先级
- **配置文件里的上限**（`config.json` 仍然只认 `close_behavior`）：与 plan 0605 对 `Reconnect`
  的处理一致 —— 默认值先落进配置模型，文件形态与配置界面一起做
- 批量选择、"全部传到对侧"一类的界面动作（`AGENTS.md` §4.0：当前界面只用于验证后端行为）

## 判据（ROADMAP 原文）

「大量小文件的吞吐**显著优于**串行请求」

**数字口径**：本机回环的一次往返在微秒级，串行与并发的差距会被系统噪声淹掉，所以先把往返
放大再比 —— 给会话接一条**带时延的链路**（`akasha_ssh::testing::slow_link`，每个方向的每一段
延后 10 ms），量同一批小文件的墙钟时间（库内 12 个 1 KiB、分档 1/2/4/8/16；端到端 12 个 1 KiB）。
判据取两个实测数字的**比值**，不等式留 2× 以上余量；随机器与负载变的数只记进基线，不作门禁
（`AGENTS.md` §7）。

## 步骤

1. **引擎：并发上限**（新文件 `akasha-ssh/src/in_flight.rs`）。`InFlight { limit, permits, live, peak }`：
   `limit` 是参数（`0` 当 `1` 用 —— "零个文件同时在搬"不是能工作的配置），`live` / `peak` 是
   读数（探针与面板都读它们）；有界入口是它的方法（`select!` 带 `biased` 地等空位，取消那一支
   先看）。`transfer()` 本身保持无上限 —— 它是一次搬运，不是一种策略。
2. **配置模型：默认值**。`Config` 多一项 `Transfer { in_flight: u32 }`，默认 **8**（见第 5 步的
   分档：16 更快，而 8 是占用与吞吐的折中 —— 上限同时是对端句柄与本机缓冲的上界）；
   **不**接进 `config.json`（非目标），app 侧照 `config::reconnect(app)` 加一个 `config::in_flight(app)`。
3. **app 接线**（`src-tauri/src/sftp.rs` / `session.rs`）。`Sftp::new(id, limit)` 建一个
   `Arc<InFlight>`，`sftp_transfer` 把它克隆进那条任务并改调有界入口；`sftp_open` 变成收
   `AppHandle` 的同步命令（只为读一次配置，仍然没有 I/O）。*验证*：E2E 从探针读到那三个数。
4. **临时名：探测 → 原子占用**（`local.rs` / `sftp.rs`）。本机 `create_new`（`O_EXCL`），
   `AlreadyExists` → 下一个候选；远端 `open_with_flags(WRITE|CREATE|EXCLUDE)`，**只有通用的
   `Failure`** 换下一个候选（v3 没有"已存在"这一档，而权限 / 超时 / 断连是确定的失败，
   换 16 个候选只会把同一次失败问 16 遍），候选用完时报**最后一次的错误原文**、不编一句
   "16 个都被占用了"。`pick_temp` 两处整份删除；取名规则仍归引擎（`temp_candidates`）。
5. **库内用例**（新文件 `akasha-ssh/tests/pipelining.rs`，6 条）：上限真的在（7 个文件、上限 3，
   目标端点同时只见到 3 个 `begin_write`，第 4 个连闸门都进不去）· 排队中被取消不碰目标
   （一个端点都没 `open` 过）· 失败不扩散 · 吞吐分档（真服务端 + `slow_link`）· 同名不撞临时名
   （两个不同的临时名，最终名的字节等于两条源之一）· 临时名不再靠探测（服务端记到的 `open`
   恰好一次、`stat` 里没有它）。前三条用可闸住的假端点，让"进不来"成为确定的事实。
6. **E2E**（新文件 `src-tauri/tests/sftp_pipelining.rs`，加进 `E2E_TARGETS`）：左栏本机 +
   右栏一台服务端（主机行指向 `slow_link` 的地址）。串行基线（逐个发、逐个等结束 → `peak == 1`）
   与并发（一口气发完 → `1 < peak <= limit`）各量一次墙钟，断言 `并发 × 2 < 串行`；
   之后拿对端**真盘**对账（12 个文件字节相同、没有临时名）。两半证据：并发读数读探针，
   文件在不在读真盘。
7. **前端壳层**：传输列表表头显示"同时在搬 N / 上限 M（最多见过 P）"，三个数都由后端给；
   刷新改为读一次 `sftp_sessions`（比原先少一条命令）。

## 实施记录（2026-09-15）

### 判据实测

**库内**（`pipelining`，6 条 / 3.8 s）。上限那一条是确定性的：7 个文件、上限 3，目标端点
**同时**只见到 3 个 `begin_write`（第 4 个连闸门都进不去），放行之后 7 个文件全部落地、
`peak` 停在 3。排队取消那一条：上限 1、第一个文件停在闸门里，取消之后第二个文件
**一个端点都没碰过**（它的路径从未被 `open`），第一个在放行后走收尾那一半 ——
目标目录里一个条目都不剩。失败不扩散：5 个文件、中间那个在第 2 次写入时失败 ——
另外 4 个字节正确落地。同名不撞临时名：两条并发传输写同一个最终名，两条的源各被闸住时，
目标目录里是**两个**不同的临时名（老实现下是同一个），放行后最终名的字节恰好等于两条源之一。

**端到端**（`sftp_pipelining`，真实 app + 一台服务端 + 一条每方向延后 10 ms 的链路，**5.07 s**）：
左栏本机、右栏那台主机（主机行指向链路的地址，app 对它一无所知）——
**串行**（逐个发、逐个等结束）12 个文件 **1.509 s**、`peak = 1`；
**并发**（一口气发完）12 个文件 **389 ms**、`peak = 8`（= 上限）；
两批之后对端**真盘**上 12 个文件的字节逐一相同、目录里没有临时名，链路共搬了 206 段。

**库内吞吐**（真服务端 + 同一条链路，12 个 1 KiB 文件）：

| 上限 | 墙钟 | 每个文件 | peak | 链路搬了多少段 |
|---|---|---|---|---|
| 1（串行基线） | 1.168 s | 97.3 ms | 1 | 116 |
| 2 | 1.159 s | 96.6 ms | 2 | 211 |
| 4 | 563 ms | 46.9 ms | 4 | 269 |
| 8（默认值） | 377 ms | 31.4 ms | 8 | 312 |
| 16 | 211 ms | 17.6 ms | 12 | 331 |

⚠️ **上限 2 与串行一样慢，这一段没有解释清楚**：上限 2 时两条传输几乎**同时**结束
（166 ms / 207 ms），而各自却都比它单独执行时（96 ms）慢一倍 —— 总工作量被序列化了，
只是平均分给了两条。同一时刻**服务端记到的两次 `open` 只差 0.08 ms**，也就是说请求确实是
并发发出去的（临时名那一条用例也靠这一点）。改动前后都复现过，换多线程 runtime 也一样。
候选解释：测试服务端串行处理请求，加上同一条连接上两个文件各自的写请求互相等待。
**默认值因此不按"饱和点"取**：取 8，理由是占用与吞吐的折中（上限同时是对端打开句柄数
与本机缓冲数的上界），而不是"再往上没有收益" —— 16 明确更快（见上表）。

### 与 ADR-0006 的偏差（已记进那份 ADR 的修订记录）

| 偏差 | 为什么 |
|---|---|
| 远端换候选的条件从"任何一种失败"收窄成"只有通用的 `Failure`" | 权限、超时、断连是**确定**的失败：换 16 个候选只是把同一次失败问 16 遍（超时那一档是 16 倍等待），而"名字被占"只能表现为 `Failure` |
| 上限加三个读数（`limit` / `live` / `peak`）进契约与探针 | "上限真的在起作用"需要一个可读的数；排队中的传输在状态枚举里与"正在搬"长得一样，分辨它们只有 `live` 这个口径 |
| `akasha-core` 的 `Transfer` 默认值不接 `config.json` | 与 plan 0605 对 `Reconnect` 的处理一致：默认值先落进模型，文件形态与配置界面一起做（非目标） |
| 面板的刷新从 `sftp_transfers` 改成 `sftp_sessions` | 传输列表与并发读数同属那个会话，分两条命令读会在界面上拼出"已经结束、而在搬的个数还是 1"这种中间态 |

### 落地时看清的三件事

1. **测试服务端把 `EXCLUDE` 当成了 `CREATE`**（`open_file` 里两者合在一个分支里 `create(true)`）：
   它就**不会**拒绝第二个同名文件，于是"抢占临时名"那条判据在库内看起来成立、实际没有 ——
   两条同名传输会交错写同一个文件而用例全绿。修好之后 `AlreadyExists` 走的是通用 `Failure`
   （`status_of` 只认 `NotFound` 与 `PermissionDenied`），**和真实 `sshd` 的形态一致**，
   所以"只有 `Failure` 换下一个候选"这条规则在库内每次都被走到。
2. **带时延链路的两个方向接反会伪装成握手实现坏了**：把"客户端读"接到"客户端写"上，
   客户端收到的就是自己刚发出去的字节，报出来的是 `Key exchange init failed` ——
   那读起来像 `russh` 的 KEX 有问题，而实际上是测试脚手架接错了两根线。
3. **链路的时延要按"段各自计时"实现**，不能写成"读一段、睡一段、写一段"的循环：
   后者会让链路自己变成一个串行瓶颈（并发发出去的请求在链路里排队），于是"并发更快"
   这件事在上限 2、4 上几乎量不出来。第一版就是那样写的。

### 顺带修掉的一处竞态（plan 0703 留下来的）

`sftp_host_to_host` 的 E2E 在本轮**整份执行**里红过一次（不是本轮改动的对象）：
右栏点「连接」时按钮**是禁用的** —— 面板用一个共享的 `busy` 判断"有命令在途"，于是
**左栏还在收尾**（`listSftp` + `refreshSides`）的那几十毫秒里，右栏的按钮点不动，
而用例的完成条件是读**探针**（plan 0703 的教训）—— 探针早就说左栏连上了。
处置：`busy` 按栏分开（一栏在连不让另一栏的按钮失去作用）—— 这也正是"两侧独立"该有的样子。
⚠️ 被判据读的**后端事实**与界面上的**可用性**之间可以有这样一道缝，它只在"一栏连完、另一栏
等着点"的顺序上暴露。

### 遗留

- **上限 2 那一段曲线没定位**（见上）：它不影响判据（并发确实显著更快），但它说明
  "往返折叠"这件事在低并发下没有按预期发生，值得单独查一次。
- **只在测试服务端上量过**：真实 `sshd` 的 `MaxSessions`、打开句柄上限与
  `limits@openssh.com` 声明的 `write_len` 都会改变"一条连接能同时扛几个文件"。
- **上限还没有文件形态**：`config.json` 仍只认 `close_behavior`（非目标），默认值之外
  没有别的取值方式。
