# Plan 0606: 关闭 `Session` 立刻断连 + 中止重连循环

- **关联**：ROADMAP 阶段 6 ·「关闭 `Session` 立刻断连，并中止该 `Session` 的重连循环」·
  ADR-0003 **D5**（连接 = 拥有它的 `Session` 的生命周期）· `scope.md` §2.2
- **前置**：plan 0605（重连循环存在，才有"中止"可言）· plan 0601（实体表与状态机）
- **状态**：已完成（2026-09-15）

## 目标

关闭一条**转发 `Session`**（面板「停止」→ `tunnel_stop`）时：

1. 它的连接**立刻关闭** —— 无宽限期、无延迟回收（`scope.md` §2.2）
2. 它正在进行的**重连循环被中止** —— 否则留下的是"没有 `Session` 的重连任务"：对一个已经
   不存在的对象反复重试、持续扰动网络，而且**没有任何地方能显示它的状态**
3. **这两件事都要能被数出来**。判据（ROADMAP 原文）是"连接数与重连任务数都归零"，而在本
   plan 之前**这两个数没有任何地方报过** —— 能观察到的只有实体表，而实体表正是被关闭命令
   自己删掉的那一份。于是"归零"既无法断言，也分不清"收干净了"与"只是从表里删掉了"。

## 非目标

- **窗口关闭的语义**：默认收托盘**不影响任何连接**（plan 0302 已定，方向相反，不得反置）
- **终端 `Session` 的关闭**：`close_session` 那条（kill + wait 回收子进程）在 plan 0204 已完成，
  它的判据由 `tab_close` / `exit_residue` 两条 E2E 看着
- 应用退出的全量回收（plan 0204 的入口）：本 plan 只把隧道那一支接进**同一条**回收路径
- 失败原因怎么呈现给用户（plan 0605 记下的未做项）

## 先定死的三件事

1. **转发 `Session` 的"关闭"入口就是 `tunnel_stop`**（面板上那个「停止」）。`close_session`
   是终端那条路，对隧道句柄答 `NotFound` —— 转发是**仅渲染**的视图，它的停止必须是它自己的
   显式动作（`scope.md` §5.6）。**把这条边界写下来**，是因为它看起来像缺口：一条隧道在
   `Sessions` 里同样是一个 `Session`，而"关闭 `Session`"这个名字很容易让人以为两者同一个入口。

2. **计数要数在资源自身上，不数实体表。** `tunnels` probe 数的是注册表里的实体，关闭一条它
   就少一行 —— 那是**命令的效果**，不是"连接断了"的证据。真正的证据是 `SshConnection` 那个
   对象还在不在：它归转发任务持有，与实体表**无关**（实体摘了，它还在）。因此两个计数是：
   - **连接数** = 进程里活着的 `SshConnection` 个数（RAII 凭证：对象析构即减一）
   - **重连任务数** = 正在运行的看护任务个数（RAII 凭证：`watch` 一返回即减一）

   两者都用 RAII 而不是"登记 + 注销两张表"：计数不可能与事实分叉，也就不需要谁记得去减。

3. **在途的尝试也要能被停止。** 停止命令目前只停"看护任务"与"已经起来的转发"，而一条
   **正在连接**（握手中）的隧道这两样都没有 —— 实体摘掉之后，那次尝试仍握着一个 socket，
   要等握手超时（D15 的 `connect_timeout` = **10 s**）才结束。这与第 1 条目标（立刻关闭）不符，
   所以**尝试在开始时就登记这条隧道的停止入口**，命令在 `select!` 里等它：收到就把尝试连
   future 一起丢掉（TCP 连接是那个 future 造的，随它一起关闭），不必等超时。

## 步骤（每步都能独立验证）

1. **`akasha-ssh`：连接的存活计数**
   - `SshConnection` 持一份 RAII 凭证（构造即加一、析构即减一）；`akasha_ssh::live_connections()`
   - 为什么不数"正在握手的"：握手中的 socket 还不是一条 `SshConnection`（D9 的类型是**已认证**的
     连接）。它由第 3 条那把停止入口停下，而不是由这个计数看着
   - 验证：`just test`
2. **app 侧：看护任务的存活计数 + 停止入口的语义扩展**
   - `watch()` 第一行取一份 RAII 凭证；`tunnel::watch_tasks()`
   - `TunnelRun` 改名 `TunnelStop`、文档改为"**这条隧道的**停止入口"（在途尝试与看护循环
     共用实体上的同一个字段）—— 名字里留着 "run" 会在尝试也开始用它之后变成一句假话
   - `tunnel_open` / `tunnel_retry`：登记停止入口 → `select!` 等尝试；被停止时返回
     `NotATunnel`（那时句柄确实已经不在册，而这条错误的文案本来就写着"已停止或未打开"）
   - 验证：`just test`
3. **探针 `residue`** → `{sshConnections, watchTasks}`：判据"两个计数都归零"的机器可读那一半
   - 新探针而不是塞进 `sessions`：那两个数说的是**这张表的两本账**（`live` 与 `registered`
     必须相等），混进别的东西会让那句不变量失效
   - 验证：真实 app 上读（第 5 步）
4. **一条回收路径**：`Tunnel::reclaim(self)`
   - `tunnel_stop` 与 `shutdown_all` 都走它。`shutdown_all` 现在靠**丢掉实体**来收尾
     （转发与停止入口各自在 drop 时收尾）—— 与 §3.3 的"drop 不能代替显式回收"是同一条纪律
   - 验证：`just test`
5. **E2E `tunnel_teardown`**（真实 app）：见「验收命令」。新增目标必须登记进
   `src-tauri/justfile` 的 `E2E_TARGETS`（漏加 = 位于门禁之外）
6. **文档同步**：本 plan 置「已完成」并移入 `archive/`（索引与 ROADMAP 指针同步）；
   ADR-0003 D5 补「实现状态」+ §14 记一行；`docs/STATUS.md` 覆盖写

真实路径的对照（Victauri E2E 逐条做同一件事）：

| 断言 | 手段 | 预期 |
|---|---|---|
| **判据：连接数归零** | 两条隧道（`-L` / `-R`）都连上 → 面板「停止」 | `residue.sshConnections` 走 **2 → 1 → 0**（关一条只少一条） |
| **判据：重连任务数归零** | 同上 | `residue.watchTasks` 同步走 **2 → 1 → 0**（关闭之前它 ≥ 1） |
| 那几条连接真的断了 | 测试服务端侧的活连接数 | 同步走 **2 → 1 → 0** —— 本进程说 0 有可能只是我们丢掉了自己的句柄 |
| 关闭一条不动另一条 | 关闭 `-R` 之后本机那条的转发端口 | 仍然 `curl` 得通（真客户端，取回本机服务的响应体） |
| `-R` 的收尾含撤销远端监听 | 关闭之后连服务端那个端口 | 连不上（那个监听还回去了） |
| 关闭是幂等的 | 对同一个句柄再 `tunnel_stop` 一次 | 返回 `Ok`；1.5 秒后再读，两个计数仍是 0（没有东西在偷偷重连） |
| **在途的尝试也被中止** | 规则指向一台"接了 TCP 就不再说话"的进程：点「重试」再点「停止」 | 那个 socket 在 **3 秒内**被对端读到 EOF（实测 **7.5 ms**；不中止的话要等握手超时） |

## 回滚

- 代码：新增集中在 `akasha-ssh` 的两个入口（存活计数、`connect_via_until`）与 app 侧的
  停止信号；对既有路径的改动是五处 —— `SshConnection` 多一个字段、`Tunnel` 的停止入口
  由"一个可替换的 `oneshot`"改成"实体自己持有的 `watch`"（`TunnelRun` → `TunnelStop` /
  `TunnelStopSignal`）、`tunnel_open` / `tunnel_retry` 各多一层 `select!`、每次
  `connect_connection` 多带一个 `cancel`、`shutdown_all` 改为显式回收。回退即恢复这五处；
  没有它，行为回到 plan 0605 的"停止只停看护与转发，在途的尝试要等握手超时"。
- 数据：**不涉及格式变更**（没有新表、没有迁移）。
- 命名：新增一个只读探针 `residue`；**没有新的命令与事件**（`TunnelState` / `tunnel_state`
  的载荷都不动）。

## 实施记录（边做边追加）

- **2026-09-15 展开**：骨架 → 进行中（补齐三件先定死的事、步骤、可粘贴的验收命令）。
- **2026-09-15 落地**：`akasha_ssh::live_connections()`（`SshConnection` 的 RAII 计数，
  构造即加一、析构即减一）与 `tunnel::watch_tasks()`（看护任务的同一套计数）；只读探针
  `residue`；`Tunnel::reclaim()` 一处收尾（`tunnel_stop` 与 `Sessions::shutdown_all` 都走它，
  退出路径不再靠 drop）；E2E 目标 `tunnel_teardown` + crate 用例两条。
- **E2E 先红了一次，红出来的正是本 plan 的要害**：在途的尝试**没有被中止** ——
  `connect_connection` 把握手放在**阻塞线程**上（`spawn_sync`），而"扔掉 await 那一侧"
  取消不了它：阻塞任务会一直执行到结束（最长一个 `connect_timeout`），那条 socket 也就一直开着。
  于是新增 `SshConnection::connect_via_until(…, cancel)`：`block_on` 的 future 里
  `select!`，取消一就绪整条建链（连同它的 socket）就结束。修之后 E2E 实测：停止到对端读到
  EOF **7.5 ms**（修之前 3 秒内看不到，因为要等握手超时）。
- **一处从 `oneshot` 改 `watch` 的返工**：先按 plan 0605 的形状"每次动作挂一个 `oneshot`
  发送端"做，写完之后发现它有**竞态** —— 看护任务挂上自己的发送端时会把尝试那个替换掉，
  于是尝试的 `select!` 两个分支同时就绪，而 `tokio::select!` 在这时**随机挑一个**：
  一次**成功**的连接因此有大约一半的机会被报成"已停止"。改成"实体自己持有一对
  `watch`、每个动作订一份接收端"之后，接收端只会在**真的被要求停止**或**实体没了**时醒。
  两条性质（订在停止之后的接收端不响、第二次停止照样响）由一条单测钉住。
- **一处刻意的边界（写进 STATUS）**：转发 `Session` 的"关闭"是 `tunnel_stop`（面板「停止」）；
  `close_session` 是终端那条（kill + wait），对隧道句柄答 `NotFound` —— 转发是**仅渲染**的
  视图，它的停止必须是它自己的显式动作（`scope.md` §5.6）。这条边界看起来像缺口，所以写下来。
- **第一段计数为什么数在资源上**：`tunnels` probe 数的是注册表里的实体，而关闭命令自己就会
  把实体摘掉 —— "表里没了"只是那条命令的效果。`residue` 数的是 `SshConnection` 对象
  （归转发任务持有）与看护任务（归 runtime 持有），两者与实体表无关。
- **E2E 实测**（`tunnel_teardown`，真实 app）：两条隧道都连上 → `residue = (2, 2)`、
  服务端也看到 2 条连接 → 关闭 `-R` → `(1, 1)`、服务端 1 条、服务端那个远端端口连不上、
  本机那条仍 `curl` 得通 → 关闭 `-L` → `(0, 0)`、服务端 0 条、两个端口都还回去了 →
  重复关闭返回 `Ok`，1.5 秒后再读仍是 `(0, 0)` → 在途的尝试（握手中停止）**7.5 ms** 内被对端
  读到 EOF。
- **门禁实测**：`just ready` **6/6**；`just test` **337 passed**（比 plan 0605 多 **4** 条）；
  `just test-e2e` 退出码 0；`pnpm build` 退出码 0（本轮前端无改动）。
