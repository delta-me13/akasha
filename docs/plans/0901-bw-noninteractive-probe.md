# Plan 0901: 实测 `bw` 对 `sshKey` 条目的非交互行为

- **关联**：ROADMAP 阶段 9 ·「**实现前先实测** `bw` 对 `sshKey` 条目的非交互行为」
- **前置**：需要**真实 vault**（这是它被推迟的原因，见 `docs/STATUS.md` 的待实测）
- **状态**：未规划（骨架）
- **展开时机**：可获得真实 vault 时（**可提前**，不阻塞其他阶段）

## 目标

把 [`../bitwarden.md`](../bitwarden.md) 列出的四项实测全部完成并**写回该文档**：

1. 未解锁时的报错形态（如何判定"需要解锁"而非"查询失败"）
2. `bw list items --raw` 的 JSON 形状（`sshKey` 字段的实际嵌套）
3. 条目是否**稳定可见**（离线 / 未同步时的行为）
4. **如何分辨专有变体与 OSS 变体**（许可证约束是硬要求：专有变体禁生产使用）

## 非目标

- 不写导入代码（plan 0903）；不写前置检查（plan 0902）
- 不实现 vault 密码学（`no`，`scope.md` §10）

## 判据（来自 ROADMAP，展开时必须变成可粘贴的验收命令）

四项实测各有**结论 + 可复现的命令与输出**，落进 [`../bitwarden.md`](../bitwarden.md)。

**第 4 项（变体判定）已实测完成**（2026-09-15，无需 vault）：判据是 `bw --help` 的命令表里
有没有 `device-approval` 那一行；两份 `cli-v2026.8.0` 资产的对比、以及"版本号分辨不出"
这两件事记在 `bitwarden.md` §2.2，判据本身由 `akasha-bw` 的 `variant` 模块与它的诱饵用例钉住。

剩下三项的门槛是**一个真实 vault**：登录之后 `bw status` 的形状、未解锁时的报错原文、
以及 `sshKey` 条目的 JSON 形状都只能在那里看到 —— 桩服务器要造出这些就得自己实现
Bitwarden 的密钥派生与加密，而那正是 `scope.md` §10 的非目标。因此本 plan 保持骨架，
展开时机是"拿到一个真实 vault"。
