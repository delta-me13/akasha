# Plan 0407: 解锁与锁定的生命周期

- **关联**：ROADMAP 阶段 4 ·「解锁与锁定的生命周期」
- **前置**：plan 0403（库能开、四套池能读写）· plan 0406（口令的受保护页）
- **状态**：未规划（骨架）
- **展开时机**：plan 0404 / 0405 之后（先让"能开、能导出、能搬走"都成立，再定"谁来持有它"）

## 目标

一个明确的答案，回答四个问题：

1. **谁持有**解好的 `Connection`（`AppHandle` 的 state？一个专用线程？）；
2. **口令从哪来**（IPC 命令的参数 → `Passphrase`；进 IPC 的那一份副本怎么擦）；
3. **什么时候锁**（用户显式锁 / 空闲超时 / 窗口关闭 / 进程退出），以及锁定时**抹掉什么**；
4. **并发**：单实例（plan 0304）与多窗口下同时解锁会怎样。

## 非目标

- 口令的输入 UI（设计稿未定，`AGENTS.md` §4.0）
- 忘记口令的恢复路径 —— ADR-0002 D5 已裁定**不可恢复**，这里不重开

## 判据（来自 ROADMAP，展开时必须变成可粘贴的验收命令）

- 解锁 → 读一次池 → 锁定之后**进程里不留机密**（判据：`VmLck` 回落到解锁前的水平）
- 口令经 IPC 进来的那些副本（反序列化缓冲、`String`）**有一个明确的处置**

## 已知需要回答的问题（展开时逐条给结论）

- ⚠️ `Passphrase::new` 在 `mlock` 失败时报错（上游没有降级路径）—— 这条要变成**用户能懂的一句话**
  （"内存锁不住，出于安全拒绝解锁"），而不是一个裸的错误码；
- 解锁是**慢**的（实测约 105 ms，ADR-0002 §7.1）：要不要挡住 UI，以及在哪一层挡；
- 锁定时**派生密钥与 SQLCipher 内部的副本**能不能真的抹掉 —— 能抹到哪一步要按 ADR-0002 D13
  的判据表重验（这是"新增用途"的又一次适用）。
