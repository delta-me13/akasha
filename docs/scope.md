## 1. 产品定位

**可搬迁的、常驻托盘的多协议终端 + 文件传输客户端。**

两条定位性约束（它们会否决具体技术方案，所以放在最前面）：

| # | 约束 | 含义 | 否决了什么 |
|---|---|---|---|
| P1 | **不依赖操作系统组件**（凭据由本程序自己保管） | 见下"豁免清单" | `keyring` 类方案（GNOME Keyring / Keychain / Credential Manager）；**核心功能**依赖外部二进制 |
| P2 | **可搬迁** | 把 bin 所在文件夹整个移动到别的路径/别的机器，**照样能开且数据还在** | 在配置或数据库里存绝对路径；把状态散落在 `$HOME` 的设计 |

### 1.1 豁免清单（明确不关心，按默认实现，不增加复杂度）

| 豁免项 | 说明 |
|---|---|
| **webview 及其依赖栈的一切写入** | GTK/dconf、fontconfig、GPU 驱动 shader cache、macOS AppKit 窗口状态保存、临时文件 —— **全部豁免**。不做环境变量重定向，不追加启动时序约束 |
| `bw` CLI（Bitwarden） | 用户自备的系统前置，见 §7。缺失时该功能不可用，这是显式选择 |

> **P3 已撤销**（2026-09-11）。原先有一条"不向数据目录之外写入，白名单只有临时目录"，
> 它引出的是"必须重定向 webview 依赖栈、必须早于 GTK/AppKit 初始化"这一整套复杂度。
> 用户明确豁免 webview 后，**判据从"没有写到别处"简化为"搬走文件夹后还能开"**。
> 这条简化砍掉了 [portable.md](./portable.md) 里大半内容。

> **P1 禁止的是"依赖 OS 凭据库"，不是"禁止一切外部前置"。** 用户自备的外部 CLI
> 是可接受的 —— 但它必须被**显式声明为前置依赖**并在启动时检查，而不是假装不存在。
> 注意 **SSH 不属于这一类**：SSH 是核心功能，已定案用纯 Rust 实现，见 §2.1。

### 1.2 命名约定：**后端名不得编码 UI 呈现方式**

这些单元在前端**渲染成什么还没定**（标签页 / 面板 / 分屏 / 独立窗口都可能）。
所以**后端类型名必须按语义命名，不得借用 UI 词汇** —— 否则前端模型定型那天，
后端里那些名字就变成了谎话，而改名要动到 IPC 类型与生成物。

| 词 | 归属 | 含义 | 不要这样用 |
|---|---|---|---|
| **`Session`** | 后端 | 用户打开的**一个工作单元**：终端 / SFTP / 端口转发 / 凭据库。**它是资源的归属单位**，生命周期约束它拥有的连接 | ~~`Tab`~~ ~~`Pane`~~ ~~`View`~~ —— 呈现方式，不是语义 |
| **`Transport`** | 后端 | **字节载体**：本地 PTY / SSH shell 通道 / 串口 | ~~`PtySession`~~ —— PTY 专属，容不下第二个后端。**原方案里这个词叫 `Session`，已改名** |
| **`Connection`** | 后端 | 一条 SSH 连接。因不做复用，一个 `Session` 可能对应一条或多条 | ~~`SshSession`~~ —— 与上层 `Session` 撞名 |
| `Tab` / 面板 / 分屏 | **前端** | 至多是前端对 `Session` 的一种呈现 | 不得出现在 `src-tauri/crates/` 的类型名里 |

配套的类型后缀：`SessionId`、`SessionKind`、`SessionRegistry`、`SessionEvent`。

> **为什么不用 `Scope` / `Workspace`**：
> `Workspace` 在本仓库已经是 **Cargo workspace** 的意思（见 `AGENTS.md` §3.1、
> ADR-0001），撞名代价很高；`Scope` 又与本文档名 `scope.md` 及
> `std::thread::scope` 都太近。命名要一并躲开**仓库内既有的词**，不只是躲开 UI 词。

**由此推出一条可执行约束**（已落地，规则表见 `AGENTS.md` §6）：

| 规则 | 拦截 |
|---|---|
| `no-ui-vocab-in-types` | `src-tauri/crates/**` 与 `src-tauri/src/**` 的类型名中出现 `Tab` / `Pane` / `Window` / `View` |

### 1.3 UI 的现状：**当前界面只是功能验证壳层**

**正式 UI 的布局、视觉与交互尚未有设计稿。** `src/**` 里现有的界面（标签栏、状态栏、配色、
空状态文案……）**只有一用途**：让后端行为能被看见、能被验证 —— 开了几个会话、谁还活着、
字节有没有流起来。它**不是**产品形态，也不构成任何约束：

- **不要**照着它推导设计系统或"既有风格"，也不要为了"和现有 UI 一致"而把一个本该改的
  交互留下来；将来按设计稿重做界面时，**该删的是布局与样式，不该动的是契约**。
- 前端改动的判据是"**这条后端行为能不能被验证**"，不是"好不好看"。在它上面做视觉打磨，
  等于给一份会被整体替换的东西加细节。
- 后端**不得**依赖前端的呈现方式（§1.2）：`src-tauri` 的命令与事件、`Session` 的状态机、
  收尾路径，都应当在界面被整体换掉之后**原样可用**。
- 反过来说，**验证用的探针与选择器可以有**（`window.__akashaTerminal`、
  `.tab-pane.is-active …`），但它们是**测试的接口**，不是"UI 规范"。

> 规则侧写进 [`AGENTS.md`](../AGENTS.md) §4.0；重做界面属于**尚未规划**的工作
> （没有设计稿就没有验收标准，因此不进 `ROADMAP.md`）。

## 2. 后端（三个）

| 后端 | v1 | 说明 |
|---|---|---|
| **local** | ✅ | 本地 PTY |
| **ssh** | ✅ | **纯 Rust（`russh`）**，不调系统 `ssh`。含跳板、端口转发 |
| **serial** | ✅ | 串口（波特率/数据位/校验/流控） |

**共同抽象**：一个**窄**的 `Transport` trait（字节载体），而不是 PTY 专属 trait。
命名理由见 §1.2。

```
Transport: write(bytes) / output_stream() / resize(尽力) / shutdown() / exited()
```

- 能力差异**用 capability flag 表达**，不要用"多几个方法都得实现一遍"。
  serial 没有窗口尺寸、没有信号、没有退出码；SSH 没有本地进程语义。
- 这个抽象必须在 `src-tauri/crates/akasha-pty` 落成**通用**形态，否则第二个后端到来时要重构。

**平台差异（不是"编译一下就有"）**：

| 后端 | Linux | Windows | macOS | Android |
|---|---|---|---|---|
| local | ✅ | ✅ ConPTY | ✅ | ❌ **需独立实现** |
| ssh | ✅ | ✅ | ✅ | ✅ 可共享 |
| serial | ✅ | ✅ | ✅ | ❌ **需 USB Host + JNI** |

- **Android 上的 local 拿不到 `/dev/ptmx`**（SELinux 沙箱）。Termux 能用 PTY 是因为它
  自带 userland bootstrap，不是普通 app 的路径。
- Android 暂定 `later`，v1 **只保证 trait 边界能容纳它，不写任何 Android 代码**。
- 「Android 只做 ssh/sftp」是可接受的降级形态，但必须是**显式决定**，不能是意外结果。

### 2.1 SSH 实现：纯 Rust（`russh`）—— **已定案**

**不调用系统 `ssh` 二进制。** 理由：

- SSH 是**核心**功能，不像 Bitwarden 可选。把核心功能押在外部二进制上（版本差异、
  参数行为差异、缺失时的降级路径）风险远大于自己实现。
- `russh` 走 `ring` / `aws-lc-rs`，**不引入 OpenSSL**；若选 `ssh2`/libssh2 则会
  绑上 OpenSSL，给四个平台的交叉编译平添负担。

**必须接受的代价**：`~/.ssh/config` 的 `Include` / `Match` / `Host *` 优先级
**没有白捡的解析器了**（原先设想的 `ssh -G` 需要系统 `ssh`）。这条见 §8 风险 4。

### 2.2 SSH 端口转发

| 类型 | 机制 | v1 |
|---|---|---|
| **本地转发**（`-L`） | `direct-tcpip` channel | ✅ |
| **远程转发**（`-R`） | `tcpip-forward` 全局请求 + 处理 `forwarded-tcpip` channel | ✅ |
| **动态转发**（`-D`，SOCKS5） | 本地 SOCKS5 服务端 + `direct-tcpip` | ✅ |

#### 一个原语服务三处（这条决定了实现顺序）

**`direct-tcpip` channel 链式串接是同一个原语**，本项目有三处需要它：

1. **跳板 / ProxyJump**（§2）
2. **SFTP host↔host 的 B 档**（§4.1）
3. **SSH 本地转发**（本节）

因此它应当**只实现一次**，落在 `src-tauri/crates/akasha-ssh` 里，三处复用。
先实现跳板，等于顺手拿到另外两处的地基。

> 例外：**远程转发（`-R`）是另一套机制** —— 它由服务端发起连接
> （`forwarded-tcpip`），不能复用上面这条路径。别把它和本地转发混为一谈。

#### 转发不属于终端，它是一个独立 Session

**一条转发规则是一个独立的 Session**，不是某个终端 Session 的附属物。两者各自持有自己的
连接，互不影响：

- 关掉**终端** Session → 只关它自己的连接，**不影响任何转发 Session**
- 关掉**转发** Session → 只关它自己的连接，**不影响任何终端 Session**

数据模型上因此要有独立的**"隧道"实体**，而不是终端 `Session` 的一个属性。

#### 连接的生命周期 = 拥有它的 Session 的生命周期（**已定案**）

| 事件 | 该 Session 的连接 |
|---|---|
| **关闭 Session**（终端或转发） | **立刻关闭** —— 无宽限期、无延迟回收 |
| 窗口关闭（默认 = 收托盘 = 隐藏） | **不受影响**（Session 还在） |
| 应用退出 | 全部关闭，零残留 |

**这条统一了 §5 的托盘语义**：托盘之所以有意义，正是因为它**隐藏**窗口而不是销毁
—— 窗口隐藏时 Session 仍在，连接因此存活。

> ⚠️ 由此推出一条硬约束：**托盘必须隐藏窗口，不能销毁窗口。** 销毁会连带销毁所有
> Session，按上表就会**立刻关掉全部连接**，直接抵消托盘的意义。这把"隐藏 vs 销毁"从
> 实现偏好升级成了**语义要求**（见 §5.5）。

**关闭 Session 还必须中止该 Session 正在进行的重连循环。** 否则会留下一个"没有 Session 的重连
任务"：它在重试一个已经不存在的东西，白白扰动网络，而且**没有任何地方能显示它的
状态** —— 正好落进下面「失败必须可见」要防的那个坑。

同理，关闭 Session 会**中止该 Session 上正在进行的一切**（例如未完成的 SFTP 传输）。
部分文件的处置见 §4.2。

#### 连接模型（**已定案**）：不复用，一实体一连接

**每个终端会话与每条转发规则各自建立独立的 SSH 连接**，不做到同一主机的连接复用
（multiplexing）。选简单方案：没有连接池，没有"一条断全断"的耦合，
每条隧道可独立重启而不影响其他。

> ⚠️ **它有一个必须处理的副作用**：到同一主机开三个标签会**握手认证三次**。
> 若该主机用密码或 2FA，用户会被问三次 —— 这不可接受。因此需要：

| 手段 | 说明 |
|---|---|
| **内存凭据缓存** | 解锁后的私钥/口令在**进程内存**中按主机缓存，供后续连接复用。**绝不落盘**（与 §6「口令不落盘」一致） |
| SSH agent | 用户配置了 agent 时认证天然不重复问 —— 最干净的路径，应优先支持 |
| known_hosts 缓存 | host key 校验结果存进库，避免每次连接重新确认 |

#### 断线重连（**已定案**）：有限次，然后标记失败

**有限次重连（带退避）→ 放弃 → 标记为 `失败`。** 不做无限重连（避免后台无谓重试
与惊扰防火墙）。

⚠️ **"标记失败"必须是可见的**，否则就是最危险的失败模式：用户以为隧道还在转发，
实际早已死掉，直到某天发现连不通才察觉。

- 后端要有显式状态机：`连接中 / 已连接 / 重连中(第 n 次) / 失败 / 已停止`
- 状态变化要**发事件**（UI 未做不影响后端先发 —— 别等到做 UI 时才补）
- 托盘菜单要能看到失败项（§5）
- 提供**手动重试**动作：自动放弃的前提是用户能一键再试
- **默认 3 次，指数退避**；参数可配置（给默认值，但不要硬编码）

## 3. 配置与凭据池

四套独立的池，都存 SQLite（见 §6）：

| 池 | 内容 | CRUD |
|---|---|---|
| **密钥池**（本地） | 名称/私钥/公钥/备注/关联主机 | ✅ |
| **ssh 配置池** | 名称/host/port/user/认证方式/跳板 | ✅ |
| **serial 配置池** | 名称/端口/波特率/数据位/停止位/校验/流控 | ✅ |
| **端口转发规则池** | 名称/方向(L/R/D)/绑定地址与端口/目标/所属主机/自启 | ✅ |

- 私钥**默认不落盘到临时文件**：建立连接时在内存中交给 SSH 层，不留中间文件。
  它在进程里也只以**受保护页**的形态存在（与口令同一套，ADR-0002 D13）。
- **不许在库里存绝对路径**（P2 的要求）。路径一律运行时相对可执行文件推导。
  这条由两条机器检查守着：**列名**不许像路径、库里的**值**不许提到我们的数据目录。
  唯一的例外是 serial 的 `port` —— 它是**操作系统给的设备名**（`/dev/ttyUSB0` / `COM3`），
  不是我们的文件位置（换台机器它可能不存在，但那不是"搬家之后才失效"）。
- 池的**关系与取值域由库自己拦**（`STRICT` 表 + `CHECK` + 外键 `RESTRICT`，ADR-0002 D14）：
  重名、端口越界、`dynamic` 带目标、跳板自环、删除还被引用的行 —— 一律是**明确错误**，
  而不是静默改写。序列跳板链的成环由写入路径走链挡住（库表达不了递归）。
- ssh 配置池的字段集**对齐 `~/.ssh/config` 的能力子集**，并保留"从系统 ssh config
  导入"的位置（导入 ≠ 同步，导入是一次性快照）。**已定：只支持受限子集**，
  遇 `Match`/`Include` 显式报错而非静默跳过 —— 见 §8 风险 4。

## 4. 文件传输（SFTP）

**形态**：双栏，左右各自从池里选主机（类似 Termius 的 sftp 页）。

| 方向 | v1 | 说明 |
|---|---|---|
| local ↔ host | ✅ | 双向 |
| host ↔ host | ✅ | 见下 |

### 4.1 host↔host 的拓扑（已定：优先直连，失败回退中转）

**前提事实**：SFTP **协议层面没有 server-to-server copy**，只有
`open/read/write/close/stat/rename`。任何两个 SFTP 服务器之间的传输**必须**由客户端驱动，
字节必然流经本机。这不是实现问题，是协议问题。

在这个前提下有两档，**两档都实现，运行时优先 B**：

| 档 | 机制 | 本机网络开销 | 前置条件 |
|---|---|---|---|
| **B（优先）** | 在到 A 的 SSH 连接上开 `direct-tcpip` channel 直通 B，SFTP 跑在隧道里 | **1×**（只需上到 A） | A 必须能连到 B |
| **A（回退）** | 内存 relay：读 A → 写 B | 2×（下 A + 上 B） | 无。**永远可用** |

- **B 并不绕开本机**：它把本机带宽砍半，并解除"本机必须能直达 B"的限制。
  真要"数据完全不经过本机"只能靠在 A 上执行 `rsync`/`scp`（需要 A↔B 互信、
  进度只能解析远端输出），**列为非目标**。
- **无论哪档都不落盘**：全程流式，不经临时文件。
- 传输引擎必须支持**并发 in-flight 请求**——多小文件的往返开销会主导耗时，
  拓扑再好也不能弥补串行请求。
- B 档复用的是 §2.2 里那个 `direct-tcpip` 原语。

### 4.2 传输的落盘方式（已定：按通行做法）

**一律先写临时名，完成后原子重命名。**

| 时机 | 行为 |
|---|---|
| 传输中 | 写到目标目录下的临时名（如 `.name.part`） |
| 成功 | 原子 `rename` 成最终名 |
| 失败 / 取消 / **关闭 Session** | **删除临时文件** |

**为什么不直接写最终名**：

1. 半截文件不会伪装成完整文件 —— **用户看到最终名就等于成功**，这是最容易被误导的地方
2. 原子重命名给出"存在即完整"这个不变量
3. 关闭 Session 时的清理是确定的：只需删掉临时名，不需要猜测进度

> **不做断点续传**（`later`）。它是 `.part` 命名的常见附带能力，但需要额外记录
> 偏移量与远端校验，不是"顺手就能有"的。

## 5. Session 模型、应用生命周期与系统托盘

**这一节是跨领域的约束，不是 UI 功能** —— 它决定**什么资源归谁所有、何时该死**。

### 5.1 统一的 Session 模型（后端必须为此解耦）

产品形态参考 Termius：**终端、SFTP、凭据库、端口转发各自是独立的 Session**，
不是"终端 Session 上挂一堆附件"。因此后端模型**不能以终端为中心**。

**Session 是资源的归属单位** —— 谁拥有连接、谁负责回收，都按 Session 算：

| Session 类型 | 它拥有的资源 |
|---|---|
| 终端 | 一条 `Transport`（本地 PTY 或 SSH shell）+ 它的连接 |
| SFTP | 双栏各自的主机连接 + 传输任务 |
| 端口转发 | 一条或多条隧道（每条规则一条连接） |
| 凭据库 | 无长连接（只有 SQLite） |

**对后端的三条要求：**

1. **资源挂在 Session 上**，不挂在"当前选中项"或全局单例上 —— 后端不得假设
   "同一时刻只有一个终端"，也不得假设"先有终端才有连接"。
2. **事件按 `SessionId` 路由**，不是全局广播后由前端过滤 —— 否则多 Session 并行时会串。
3. **Session 类型之间互不依赖**：SFTP Session 不需要先开一个终端；转发 Session 也不需要。

> 这条对**实现顺序**有直接影响：`akasha-core` 里的 Session 模型要**先立起来**，
> 否则第一个后端就会把"终端 = 应用"的假设写进架构，之后拆它很贵。

### 5.2 托盘行为

| 行为 | 默认 | 可配置 |
|---|---|---|
| 点窗口关闭按钮 | **收到系统托盘**（不退出） | ✅ 可改为"直接退出"（配置 UI 暂不讨论，先做后端） |
| 托盘菜单 | 显示/隐藏窗口、**隧道列表与各自状态**、退出 | — |
| 退出应用 | 真正退出（此时才回收一切，见 §8 风险 1） | — |

> ⚠️ **托盘是"失败可见"的落点。** §2.2 定了"有限次重连后标记失败"，
> 而那个"标记"必须让用户看得见 —— 托盘菜单是 v1 唯一能承载它的地方。
> 否则就是最危险的失败模式：用户以为隧道在转发，实际早已死掉。

### 5.3 为什么端口转发需要托盘

**先分清"关窗口"与"关 Session"，这两件事的后果相反：**

| 动作 | 连接 |
|---|---|
| 关 **Session** | **立刻断**（§2.2，连接归 Session 所有） |
| 关 **窗口**（默认收托盘） | **不断** —— 否则用户一收托盘隧道就全没了 |

所以托盘对端口转发是**功能前提**，不是体验偏好：它保住的是"窗口隐藏期间 Session 不被
销毁"。这正是 §5.5 要求**隐藏而非销毁**的根本原因。

### 5.4 由此产生的三条硬要求

1. **窗口关闭 ≠ 进程退出。** 必须拦截 `WindowEvent::CloseRequested`，先 `hide()`、**成功才**
   `prevent_close()`（配置成"直接退出"时放行）。⚠️ **不要**再挂 `RunEvent::ExitRequested` 去
   `prevent_exit()`：`AppHandle::exit()` **同样**会触发它，拦下去会把托盘菜单的"退出"一起
   拦掉。理由与实测见 [`docs/plans/archive/0302`](./plans/archive/0302-hide-not-destroy.md)。
2. **PTY 会话与隧道在窗口关闭时不得被回收。** 这条与原本的"窗口关闭即收尸"规则
   **方向相反**，必须显式写进规范，否则一个"勤快"的清理逻辑会把隧道杀掉。
   见 §8 风险 1。
3. **真正退出时必须零残留。** 托盘退出 / app 重载 / panic 三条路径都要显式 kill + wait。

### 5.5 实现注意

- Linux 托盘需要 **`libayatana-appindicator3`**（系统库，已在 CI 的 apt 依赖里）。
  ⚠️ 加载是**运行时 dlopen**，顺序为 `libayatana-appindicator3.so.1` → `libappindicator3.so.1`
  —— 只装了后者（2012 年的老库）的机器也能起，但那是**不支持的那条路**（坑 #61）。
- Linux 上**图标要落盘**：`tray-icon` 会写到 `$XDG_RUNTIME_DIR/tray-icon/<name>.png`
  （只读 runtime dir / 容器里写不了）。所以托盘属于**可选能力**：建不起来只该记一条日志，
  且此时**不能**把"关窗口"做成隐藏 —— 否则窗口再也叫不回来（坑 #60）。
- 隐藏窗口 vs 销毁窗口：**必须用隐藏**。这不只是"更简单" —— 见 §2.2：
  销毁窗口会连带销毁所有 Session，按「连接 = Session 生命周期」的规则**立刻关掉全部隧道**，
  直接抵消托盘的意义。附带好处是 webview 状态（xterm 回滚缓冲）得以保留。
- 托盘图标在 macOS/Linux 上对尺寸与模板图标有额外要求，属 UI 阶段。
- **单实例**（已定案）：第二个实例**唤起已有窗口**再自己退出，而不是各跑一套隧道。
  ⚠️ "唤起"必须包含**显示** —— 只置前叫不回一个隐藏着的窗口。落地见
  [`plans/archive/0304`](./plans/archive/0304-single-instance.md)。

### 5.6 前端标签页的分类：关标签页 ≠ 关窗口 ≠ 关 Session

后端有四种 `Session`（§5.1），但**前端标签页只有两类**，而它们的生命周期语义**相反** ——
不分开写清楚，"关掉一个标签"就会被顺手实现成"关掉一切"或者"什么都不关"（已定案）：

| 前端标签页 | 后端 | 关闭按钮 | 关掉它的后果 |
|---|---|---|---|
| **三大终端**（local / ssh / serial） | 一个 `Session`，拥有一条 `Transport` | **有** | **立刻丢弃该 `Session`**：kill + wait 收尸、摘牌、撤销兜底登记。无宽限期、无二次确认。**只丢它自己** |
| SSH 转发（本地 / 远程 / 动态） | `Session`（Tunnel） | **无** | 前端只是**客户端视图**：后端服务照常运行 |
| 密码库 | `Session`（Vault） | **无** | 同上（它没有长连接，只有 SQLite） |
| 文件传输（SFTP 等） | `Session`（Sftp） | **无** | 同上：**正在进行的传输不因前端关掉而中止** —— 取消是显式动作（§4.2） |

- **为什么终端是"关了就丢"**：一个终端标签页 = 用户打开的一个工作单元，关掉它就是"不要了"。
  里面还跑着东西时**不**再问一遍 —— `×` 本身就是那个决定。
- **为什么其余三类是"仅渲染"**：它们是**后端服务的视图**（客户端 / 服务端分家）。
  关掉前端不该打断后端正在做的事，否则用户会在一个毫不相关的动作里丢掉一条正在传的文件。
- **由此推出的一条硬约束**：转发与传输**必须有自己的停止动作**，不能靠"前端没了"来收尾
  —— 转发见 §2.2「关闭 Session」（阶段 6 的 0606），传输取消见 §4.2。
- ⚠️ **三个动作别混**：关**标签页** = 丢弃这一个 `Session`；关**窗口**（默认）= 收托盘，
  `Session` 全部存活（§5.2 / §5.3）；**退出应用** = 全部回收、零残留（§8 风险 1）。
  可执行的那一行在 [`AGENTS.md`](../AGENTS.md) §3.3 的事件表里。

#### 反方向：**会话自己结束**时，标签页跟着关（已定案）

终端标签页与它自己的 `Session` **同生命期**。所以除了"关标签页 → 丢弃会话"，还有反方向：

| 谁先结束 | 另一个怎么办 |
|---|---|
| 用户关标签页 | 后端**立刻丢弃**那个会话（kill + wait 收尸、摘牌、撤销兜底登记） |
| **会话自己结束**（用户在终端里敲 `exit`、shell 崩溃、PTY 关闭） | 后端**立刻收掉它**（同上），并发一个事件 —— 前端据此**关掉那个标签页** |

- **"自己结束"这条路上没人等结果**，所以它更要显式收尾：不 `wait` 会留僵尸，不撤销兜底登记
  会让端到端退出时对着一个**已被复用的 pid** 再发一次 SIGKILL。
- **不给它做"已退出"的中间态**（灰掉的标签页、`[进程已结束]` 之类）：要展示什么、怎么展示，
  属于正式 UI 的事（§1.3），现在直接关掉。
- **不适用**于其余三类标签页：它们没有"会话自己结束"这回事 —— 后端服务活着，
  前端视图就只是视图。

> ⚠️ 会话里若还有别的进程握着 PTY（例如忽略 SIGHUP 的后台作业），主端读不到 EOF，
> 会话就**不算**结束、标签页也**不该**关 —— 真实终端同样是这个行为。

## 6. 存储与加密

| 项 | 决定 |
|---|---|
| 引擎 | SQLite（`rusqlite`），**同步 API + 专用线程**，不用 `sqlx`（SQLCipher 支持弱） |
| 加密 | **SQLCipher**，feature `bundled-sqlcipher-vendored-openssl`（vendored 是必须的：否则交叉编译撞系统 OpenSSL） |
| 密钥来源 | **用户口令 → KDF → 库密钥**（因为 P1 排除了 OS keychain）。口令不落盘；口令本体在内存里也**被护住**（锁定、静止不可读、不进 core dump，见 ADR-0002 §7.2） |
| dump | 支持 |
| 导出 | 可选**是否加密**导出文件 |

- **`bundled-sqlcipher` 单独用不够**：必须有 `-vendored-openssl`，否则四平台构建会撞上
  系统 OpenSSL 的交叉编译问题。
- **导出是最高危的操作**，因为库里含私钥：
  - 加密导出：独立口令（不复用库口令），自包含，可直接给另一台机器用
  - 明文导出：**必须显式二次确认 + 明示内容含私钥**，不许作为默认选项
- 库文件是**唯一真相源**，不是缓存；**四套池与 BW 缓存都在同一个库文件里**（`akasha.db`）。
- **库里不存绝对路径**（P2）。
- **取证值的理由与否决路见 [ADR-0002](./adr/0002-secret-storage.md)**（实现中）：KDF 参数与盐的
  存放位置、**不启用 WAL**、导出容器的格式与版本字段、口令经 C API 送入库、空口令必须被拒。
  本节只留结论 —— 那些是数据文件格式，改它们要迁移用户数据。

## 7. Bitwarden 集成

| 项 | 决定 |
|---|---|
| 接入方式 | **`bw` CLI**（官方）。**用户自备的系统前置，不由本程序打包** |
| 为什么必须自备 | **许可证**：专有变体禁止分发（2.3(i)）与生产使用（2.1）—— **法律要求，不是偏好** |
| 前置检查 | 探测 `bw` **及其变体**；缺失时明确报"需安装哪个变体"，不静默失败 |
| 方向 | **v1 只读导入**（Bitwarden → 本池）。**不写回 Bitwarden** |
| 性质 | 独立导入池，**与本地密钥池之间没有任何同步机制**（是"快照 + 显式导入"，不是 cache） |
| 本地池 | 完整 CRUD，**与 Bitwarden 无关，永远可用** |
| 导入池 | 可导入、可删、可改备注；**不回写上游** |
| 离线 | 有加密离线缓存；缓存**放在同一个库里**（"与本地池同级"的具体含义：同一把口令派生的密钥、同一次解锁，见 [ADR-0002](./adr/0002-secret-storage.md)） |
| 加密 | 由 Bitwarden 负责，本程序**只读写接口**，不实现 vault 密码学（`no`，见 §10） |

> **接受的代价**：未装 `bw` 的机器上该功能**整体不可用**。这是显式选择 ——
> 所以前置检查必须给出可读报错（含**该装哪个变体**），而不是静默禁用。

**展开见 [`bitwarden.md`](./bitwarden.md)**：许可证条款原文与三条替代路、
四条技术路的核实结果、`sshKey` 字段结构、**`revisionDate` 与 `fingerprint`
的职责划分**（含 `fingerprint` 独有的**离线自检**能力）、会话与写入范围、
以及实现前必须实测的四项。

## 8. 已识别的风险与设计约束

### 风险 1 — 托盘与"窗口关闭即收尸"**方向相反**（✅ 已修复 2026-09-11）

原 `AGENTS.md` §3.3 要求"窗口关闭"是三条收尸路径之一，§7 的 DoD 更要求
"关闭后无残留 PTY 子进程"。**这与 §5 的托盘需求正好相反** ——
一个照着原规范实现的清理逻辑，会把用户正在用的隧道和终端全部杀掉。

**已落到规范**（`AGENTS.md` §3.3 表格 + §7 的 DoD 条目）：

| 事件 | PTY / 隧道 | 进程 |
|---|---|---|
| 窗口关闭（默认 = 收托盘） | **必须存活** | 存活 |
| 窗口关闭（配置为"直接退出"） | 回收 | 退出 |
| **真正退出**（托盘退出 / app 重载 / panic） | **必须回收，零残留** | 退出 |

验收方式相应改变：`introspect { action: "processes" }` 要在**真正退出之后**确认零残留；
而在"收托盘"状态下，**存在子进程是预期行为，不是 bug**
（规范里已写明，否则它会被当成 bug 报上来）。

> 这条留档而不是删掉，因为它是"规范与需求反向"的实例 —— 下次出现同类冲突时，
> 处置方式应当一样：**改规范，并在规范里写明反向的反直觉点。**

### 风险 2 — 可搬迁 vs. 数据目录可写性

"数据存在 bin 所在文件夹" 在以下场景**会失败**：macOS `.app`（只读 + 签名）、
Linux 装到 `/usr/bin`、Windows 装到 `Program Files`。

**方案**：可搬迁**由标记触发**，而非无条件。
- bin 同目录存在数据目录（或便携标记文件）→ 用它
- 否则 → 退回 OS 标准数据目录
- 便携模式下若检测到**不可写** → **启动即明确报错**

第 3 条是重点：**不要静默退回 OS 目录**。那会让用户以为数据在 U 盘上、实际写在
本地磁盘 —— 他拔了 U 盘，数据没了，而他不知道。详见 [`portable.md`](./portable.md)。

### 风险 3 — Bitwarden 接入：**已定案**（2026-09-11）

结论：**`bw` CLI 作为用户自备的系统前置（不打包）+ v1 只读导入**，见 §7。

**决定性理由是许可证**（专有变体 2.1 禁生产、2.3(i) 禁分发），不是体积。
条款原文、四条技术路的核实结果与"为什么 Raycast 的先例不适用"，
留档于 [`bitwarden.md`](./bitwarden.md)。

### 风险 4 — 纯 Rust SSH 之后：`~/.ssh/config` 怎么做（**已定案**）

`ssh -G` 那条捷径随 §2.1 的定案**作废**了（它需要系统 `ssh`）。

**决定：只支持受限子集** —— `Host` / `HostName` / `User` / `Port` /
`IdentityFile` / `ProxyJump`；**明确不支持 `Match` 与 `Include`**。

| 出路 | 取舍 |
|---|---|
| ~~自己实现完整解析器~~ | 否决：**本项目最容易被低估的一块复杂度**，优先级规则很绕，且错了会**静默连错主机** |
| ~~完全不读系统 config~~ | 否决：体验受损，用户已有的配置要手工重录 |
| ✅ **受限子集** | 覆盖面够用，且能把"不支持"变成**显式报错而非静默误解析** —— 这是它优于前两条的关键 |

**两条必须配套**（否则"受限"会变成"悄悄错"）：

1. 遇到 `Match` / `Include` 时**显式报错或明确警告**，绝不静默跳过。
2. UI 上列出**支持哪些指令**，让用户知道边界在哪。

### 风险 5 — 其他系统组件依赖

| 依赖 | 平台 | 可避免？ |
|---|---|---|
| WebKitGTK / GTK3 / GLib / fontconfig | Linux | ❌ 不可避免（用 Tauri 就得有）—— 属 §1.1 webview 豁免 |
| WebView2 runtime | Windows | ❌ 同上 |
| **`libayatana-appindicator3`**（托盘，§5） | Linux | ❌ 不可避免（任何 Linux 托盘应用都需要） |
| **`libudev`**（`serialport` 的端口枚举） | Linux | ✅ **已定：做成 cargo feature，仅 Linux 编译时启用**（见下） |
| OpenSSL | 全平台 | ✅ 已避免：SQLCipher 用 `-vendored-openssl`，SSH 用 `russh`（`ring`/`aws-lc-rs`） |
| `bw` CLI | 全平台 | 已定案为**刻意的例外**（§7） |
| 系统 `ssh` | 全平台 | ✅ **不再需要**（§2.1 定案纯 Rust） |

> 注意 OpenSSL 那一行不是"不可避免"，而是**我们自己选出来的**：选 `russh` 而非
> `ssh2`、记得 SQLCipher 的 vendored feature，就不会多一个跨平台链接负担。

> **`libudev` 的处置（已定案）**：`serialport` 在 Linux 上靠 libudev 枚举端口，
> 这是 webview 之外的独立系统库。**把它做成 cargo feature，只在
> `target_os = "linux"` 时实际编译** —— 于是 Windows / macOS / Android 的构建
> 完全不碰它。副作用：Linux 上串口热插拔事件依赖 libudev，若某些发行版缺失，
> 串口列表需要退化为"手动指定路径"而不是硬失败。

## 9. 平台矩阵

| 平台 | v1 | 备注 |
|---|---|---|
| Linux | ✅ | 开发主机；托盘需 `libayatana-appindicator3` |
| Windows | ✅ | 需验证 ConPTY 与托盘 |
| macOS | ✅ | 交叉编译**不可能**，只能 macOS runner / 真机；数据目录在 `.app` **旁边** |
| Android | `later` | 只留 trait 边界，见 §2。托盘与端口转发的形态未评估 |

**CI 平台矩阵要在阶段 1 就建立**，不能像早期 ROADMAP 那样放到收尾——
PTY/serial/ssh 的平台差异是**主体工作量**，把它留到最后等于把最大的坑留在最晚。

**交叉编译现实**（决定工具选型）：

| 目标 | Linux 上 `cargo check --target` | Linux 上出包 | 手段 |
|---|---|---|---|
| Linux | ✅ 原生 | ✅ | — |
| Windows | ✅（`check` 不链接，只需 `rustup target add`） | ❌ | CI `windows-latest` |
| macOS | ✅ | ❌ | CI `macos-latest`（需 macOS SDK + 许可） |
| Android | ✅ | ✅ | `cargo-ndk` + NDK + `tauri android` |

> 因此 **`cargo-xwin` 不是当前需要的工具**：`cargo check --target` 已覆盖"挡 cfg 错误"
> 这个 90% 的诉求。只有当某个依赖的 C build script 在 check 阶段就失败时才引入它
> （它解决的是**链接**问题，救不了 Tauri 的 Windows 打包——WiX/NSIS/WebView2 bootstrapper
> 都要求 Windows 主机）。

## 10. 非目标与延后项

**逐条标注是 `no`（永不做）还是 `later`（推迟，可重开）** —— 见开头图例。

| 项 | 类别 | 理由 |
|---|---|---|
| 自实现 Bitwarden vault 密码学 | `no` | §7。错了即灾难；由 Bitwarden 负责 |
| **打包 `bw`（专有变体）** | `no` | **法律要求**：专有变体禁分发（2.3(i)）与生产使用（2.1）。见 [`bitwarden.md`](./bitwarden.md) §2 |
| **打包 `bw-oss-*`（GPL-3.0-only）** | `later` | 合法，但会把 GPL 义务带进我们的分发；非必要不做（[`bitwarden.md`](./bitwarden.md) §2） |
| 调用系统 `ssh` 二进制 | `no` | §2.1。核心功能不押在外部二进制上 |
| host↔host **真不中转**（在 A 上跑 `rsync`） | `no` | §4.1。需 A↔B 互信，进度不可控。B 档已覆盖带宽诉求 |
| 依赖 OS 凭据库 | `no` | P1 |
| **为 webview 依赖栈做环境重定向** | `no` | §1.1 已豁免。不要为已豁免的东西增加启动时序复杂度 |
| 插件系统 | `no` | 每次都会被提，但会与"凭据池不漂移"的约束冲突 |
| 自带运行时（Node/Python）作为应用依赖 | `no` | P1。`bw` 不打包（同上前两条） |
| **写回 Bitwarden**（创建/修改条目） | `later` | v1 只读导入；写回引入并发/冲突/格式兼容三类问题 |
| 从系统 `~/.ssh/config` **完整**导入（`Match` / `Include`） | `later` | §8 风险 4。v1 已定只支持受限子集，且遇不支持指令**显式报错** |
| **端口敲门**（Port knocking） | `later` | v1 不承诺 —— 原先列在 §2 的 ssh 能力行与 §3 的配置池字段里，2026-09-12 **收回**。它对连接路径是一条独立原语（连接前先发一串序列），不阻塞任何其它 v1 能力 |
| **SFTP 断点续传** | `later` | §4.2。需要记录偏移量与远端校验，不是顺手就能有 |
| 无窗口/守护进程模式（headless） | `later` | 托盘已覆盖常驻诉求；真要 CLI 化再评估 |
| Android 代码 | `later` | §2。v1 只留 trait 边界 |
| 移动端（除 Android 的 ssh/sftp 外） | `later` | 未评估 |
